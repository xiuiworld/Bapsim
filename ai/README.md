# 개인 사용 패턴 Colab 실험

현재 서비스 판정은 `domain/personal_model/engine.py`의 `PersonalUsageModel`을 사용합니다. [1인 가구 중년·노년층 가상 시나리오 노트북](밥심_1인가구_중노년_가상시나리오_Colab.ipynb)은 이 코드를 그대로 포함하므로 Google Colab에서 파일을 열고 **런타임 → 모두 실행**하면 별도 패키지·저장소 인증 없이 재현됩니다. 노트북의 실행 결과와 생성 코드는 `python -m ai.build_personal_usage_colab`으로 다시 만들 수 있습니다. 이전 [소규모 실험 노트북](밥심_개인사용패턴_학습_Colab.ipynb)은 비교용으로 보존합니다.

- `target_cohort_experiment.py`는 1인 가구 중년·노년층의 **가상** 생활 유형 8개를 균형 있게 생성합니다. 아침 결식 가능성, 하루 한 번 사용, 이틀 간격 조리, 주말 시간 변화 등을 시험하지만 유형별 비율과 밥솥 사용 확률은 문헌에서 측정된 값이 아닙니다.
- 가상 가구마다 초기 28일을 시간 순서대로 학습하고 뒤의 28일을 평가합니다. 훈련 32가구에서 기준 확률 후보를 선택하고, 별도 보류 32가구와 생활 패턴 변화 16가구에서 확인합니다. 가구별 시드는 겹치지 않습니다.
- 고정 24시간 미사용 기준과 내부 `check_required` 후보를 비교합니다. 시간대 및 간격 판정은 현재 모델 코드를 사용합니다. 외출·통신 단절은 활동 없음으로 세지 않습니다. 포착률과 오경보율 외에 28일당 가구별 불필요한 내부 후보 수도 표시합니다.
- 훈련 가구에서만 최대 1시간의 늦은 사용 유예와 간격 분위수(현재 95%, 실험 후보 75%)를 비교합니다. 보류·생활 변화 가구의 포착과 불필요한 후보를 모두 공개합니다. 실험 후보는 운영 기본값에 자동 적용되지 않습니다.
- [결과 JSON](target_cohort_result.json)은 **가상 상황의 기능·민감도 실험**입니다. 정상적인 밥솥 미사용과 시나리오상 사용 중단은 센서 관측만으로 구별되지 않을 수 있습니다. 실제 식사·건강 상태, 실제 생활 오경보율, 휴대폰 푸시 성능을 뜻하지 않습니다. 후보 값은 운영 설정에 자동 적용되지 않습니다.

## 다조건 가상 학습과 미공개 조건 검증

[다조건 노트북](밥심_다조건_가상학습_Colab.ipynb)은 `python -m ai.build_condition_matrix_colab`으로 재생성합니다. `condition_matrix_experiment.py`는 규칙적인 아침·저녁, 하루 두 번, 격일 사용 가구를 두고 안정적 사용·늦은 사용·자연스러운 건너뜀·3일 간격 조리를 훈련 조건으로 조합합니다. 점진적 시각 이동·주말 이동·건너뜀과 늦은 사용의 결합은 후보 선택에 쓰지 않는 별도 검증 조건입니다. 시드도 분리하며 가구마다 과거 21일을 학습한 뒤 미래 21일을 평가합니다.

[다조건 결과 JSON](condition_matrix_result.json)은 모델 후보에 실제 `DetectionStateManager`의 연속 확인 규칙을 적용해 **보호자 발송 요청**을 비교합니다. 모델 내부 후보도 별도 필드로 남깁니다. 확률 기준·사용 유예·간격 분위수·연속 확인 시간과 횟수를 훈련 조건에서 선택하고 다른 가구·조건에서 확인합니다. 전송 성공은 가정하므로 실제 휴대폰 푸시 수가 아닙니다. 훈련에서 다른 후보가 근소하게 선택됐지만 별도 조건의 정상일 알림이 늘어 운영값은 바꾸지 않았습니다. [알림 가상 최적화 기록](../docs/알림_가상최적화_2026-10-03.md)에 수치와 한계를 적었습니다.

`python -m ai.robust_notification_experiment`는 사용 시각·건너뜀·개방 누락을 인위적으로 바꾼 가상 가구에서 생활 유형별 최악 손실로 설정을 선택합니다. [강건성 기록](../docs/강건_가상평가_2026-10-03.md)의 보류 복합 조건에서는 선택 후보가 더 나빠 운영 모델에 반영하지 않았습니다. 결과는 [JSON](robust_notification_result.json)에 저장됩니다.

같은 JSON의 `holdout_episodes_*`는 연속된 사용 중단 2일을 한 사건으로 묶어 최초 보호자 알림 요청의 포착 여부와 지연을 계산합니다. 보류 복합 조건 32건 중 현재 설정은 13건 포착(40.62%, 포착 건 중앙 지연 24.82시간), 실험 후보는 9건 포착(28.12%)이어서 후보를 운영에 반영하지 않았습니다. 이 값은 가상 사용 중단 라벨에 대한 결과이며, 실제 식사나 안부 확인 정확도가 아닙니다.

초기 사용 패턴을 아는 경우 Home Assistant의 `bapsim.set_initial_routine`에 밥솥 `device_id`와 한국 시간 `windows`를 지정할 수 있습니다. 예: `[{"time":"08:00","weekdays":[0,1,2,3,4,5,6]},{"time":"13:00","weekdays":[5,6]}]`는 아침은 매일, 점심은 주말만 집에서 밥솥을 쓰는 가정입니다. `0`은 월요일, `6`은 일요일이며 최대 4개 시간대를 설정합니다. 평일 외부 식사처럼 집에서 쓰지 않는 시간은 해당 요일을 제외합니다. 빈 배열로 해제할 수 있습니다. 초기 입력만으로 알림을 내지는 않고, 연결 관측과 실제 개방 이력이 쌓여야 조기 판정을 허용합니다. 외부 분석 작업자 모드에서는 설정이 MQTT 보존 메시지로 전달됩니다.

초기 입력 효과는 [초기 패턴 가상 비교](../docs/초기패턴_가상비교_2026-10-03.md)에서 같은 가상 기록의 입력 전·후를 비교했습니다. 별도 재현 24가구에서 입력 후 중단 사건 포착은 0/48에서 33/48로 바뀌었지만, 시각을 크게 잘못 입력한 조건은 0/8건이었습니다. 이 실험은 초기 학습 기간을 의도적으로 시험하므로 현장 정확도를 나타내지 않습니다.

설정한 초기 시간은 `sensor.bapsim_initial_routine`의 `routines` 속성에서 확인합니다. 마지막 입력 후 28일이 지나거나 이전 버전에서 입력 시각을 알 수 없는 경우 센서가 `review_due`를 표시합니다. 이는 검토 표시이며 자동으로 초기값을 지우거나 변경하지 않습니다. 위 서비스로 시간을 다시 입력하면 검토 시각이 갱신됩니다.

`python -m ai.benign_disruption_experiment`는 무작위 외식·늦은 사용·외출·단절을 섞어 알림 혼동을 시험합니다. [무작위 생활 교란 결과](../docs/무작위_생활교란_가상평가_2026-10-03.md)에서는 미리 알린 외출과 단절일 요청은 0건이었으나, 알리지 않은 외출과 외식에서 불필요한 요청이 남았습니다. 1시간 사용 유예 후보도 놓침·지연과 함께 비교했고 운영값은 바꾸지 않았습니다.

`python -m ai.irregular_interval_experiment`는 2일·3일·2/3일 교대 사용을 시간 단위로 재생합니다. [불규칙 간격 결과](../docs/불규칙_사용간격_가상평가_2026-10-03.md)에는 작은 표본에서 최장 간격에 좌우되는 기존 방식, 강건한 다음 간격 예측 후보, 정상 건너뜀이 잦은 스트레스 조건을 비교했습니다. 새 후보는 사건 포착을 늘렸지만 요청이 늦어지는 약점이 있어 운영값은 유지했습니다. 원자료는 [JSON](irregular_interval_result.json)입니다.

기존 [가중치 실험 노트북](밥심_가중치_실험_Colab.ipynb)과 `calibration.py`는 이전 `RuleDetector` 비교용 기록입니다. 현재 개인화 모델의 학습 결과로 사용하지 않습니다.

## 실제 기록 평가를 위한 로컬 준비

[평가 기록 규약](../docs/개인화_평가_기록_규약.md)에 가명 관측·별도 확인 라벨의 JSONL 형식과 제외 기준을 적었습니다. `python -m ai.demo_usage_records --output-dir local-data/usage-demo`로 두 가상 가구의 관측·라벨·보고서를 만들고, `python -m ai.usage_record_pipeline --help`로 별도 기록 평가 명령을 확인할 수 있습니다. 이 경로는 로컬 오프라인 평가용이며 Colab 노트북이나 운영 알림 기준을 자동으로 바꾸지 않습니다.

보고서는 모델의 내부 후보(`personal`)와 상태 관리 규칙을 통과한 발송 요청(`notification_request`)을 따로 집계합니다. 가상 날짜별 라벨과 평가 시각은 실생활 확인 자료가 아니므로 보고서 수치를 실제 정확도로 읽지 않습니다.
