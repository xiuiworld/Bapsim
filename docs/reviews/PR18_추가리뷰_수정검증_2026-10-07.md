# PR #18 추가 리뷰 수정·검증

검증일: 2026-10-07. 기준은 `integration/pre-sensor-software`의 `8eb9f94c6d1a04966ebc5c74862d9d83d36d0724`이다. 작업 전·push 전 GitHub에서 PR #18이 같은 head의 open/Draft이며 main에 병합되지 않았음을 확인했다. 이 문서와 함께 올라가는 후속 커밋이 아래 수정의 배포 기준이다.

기존 실물/시뮬레이션 사건 분리, 정상 연결 경고 제거, 외부 사건/보류 선택 목록 수정은 유지했다. `firmware/`, 입력 어댑터, 시뮬레이터, 원시 8필드 계약은 변경하지 않았다.

## 1. P1: 독립 HA 설치본 import

### 실패 재현

ZIP을 임시 디렉터리에 펼친 뒤 새 Python 프로세스를 `-I -S`로 실행했다. 저장소 및 site-packages/PYTHONPATH 없이 펼친 경로만 추가하고 필요한 HA 대체 모듈을 제공했다. `custom_components.bapsim` import가 `ModuleNotFoundError: No module named 'domain'`으로 실패했다.

### 원인·수정

- `service/ha_cooker_events.py`의 최상위 `domain` import는 개발 저장소에서만 유효했다. 개발 패키지 `service`에서는 기존 절대 import, 배포 runtime 패키지에서는 상대 import를 사용한다.
- `tests/test_ha_bundle.py`는 기존 프로세스의 모듈 캐시·저장소 경로를 공유하던 검증을 새 격리 프로세스로 바꿨다. HA 대체 모듈은 테스트 소스에서 전달하며 자식 프로세스는 저장소의 테스트 모듈도 import하지 않는다.

### 회귀 결과

ZIP 생성 성공과 설치본 로드 성공을 별도로 검증했다. 격리 프로세스에서 최상위 `domain`이 검색되지 않는 것을 확인한 후 import와 `async_setup` 모두 성공했고, 이후에도 최상위 `domain` 모듈이 생성되지 않았다. 실제 HA 설치는 수행하지 않았다.

## 2. P2: 외부 모드 사건 확인 중·완료

### 실패 재현

HA MQTT 결과에 사건을 표시·선택하고 `respond(checking)`을 호출했으나 작업자 명령은 0건이었고 작업자 사건은 `notified`에 머물렀다. 내부 workflow만 조회·변경하던 것이 원인이다.

### 원인·수정

- `service/ha_caregiver_commands.py`: 외부 모드는 만료되지 않은 실물 결과에서 정확히 하나의 사건을 선택하고 `caregiver_response` 명령을 보낸다. ID, 응답, 결과 만료 시각을 포함한다. 사건 두 개에서 선택이 없거나 잘못된 ID, 만료 결과, 명시적 simulator 응답은 거부한다.
- `workflow/notification_controls.py`: 기존 제어 계약에 별도 `caregiver_response` action과 checking/resolved 검증·명령 중복 처리를 추가했다. 기간 지정 `acknowledge`와 독립적이며 acknowledgement를 만들지 않는다.
- `service/standalone.py`: 작업자가 만료·실물 사건·현재 상태를 다시 검사하고 실제 gap/trend workflow를 변경한다. 상태를 저장한 뒤 결과와 제어 상태를 발행한다. 저장 실패는 상태를 되돌리고 거부한다. 재시작 후 같은 명령은 저장된 응답을 반환하며 사건을 다시 변경하지 않는다.
- `service/output.py`: 사건의 source/device_id/caregiver_status를 결과에 추가했다. 기존 status 의미를 유지하면서 확인 중·완료를 표시한다.
- `infrastructure/home_assistant/config/custom_components/bapsim/services.yaml`, `infrastructure/home_assistant/config/dashboards/bapsim_lab.yaml`: 서비스 대상 설명·incident_id와 확인 상태 표시를 연결했다.
- `docs/contracts/분석결과_HA_휴대폰_출력계약.md`: 생산자·소비자·영속화 계약을 함께 기록했다.

### 회귀 결과

`tests/test_external_caregiver_response.py`의 세 테스트는 실제 AnalysisService 소비자를 호출한다. 사건 1개/2개, 선택된 사건만 checking→resolved, 다른 실물 사건과 simulator 보존, 상태 출력, 각 단계의 재시작 복원, 중복 재전달, 만료·잘못된 사건 거부, 저장 실패 rollback을 검증했다. MQTT 발행 건수만 검증한 결과가 아니다. 실제 MQTT 브로커와 HA UI 버튼은 사용하지 않았다.

## 3. P2/F04: 초기 기준과 개인화 표시

### 실패 재현

초기 시간 07:00·모든 요일, 관측 3일·첫 두 날 개방의 profile은 `initial_ready=True`와 `ready=True`를 함께 반환했고 출력이 `personalized`였다. 초기 기준으로 판단할 수 있는 조건을 학습 완료 표시에도 사용한 것이 원인이다.

### 원인·수정

- `domain/personal_model/engine.py`: profile의 개인화 표시 ready는 기존 `docs/planning/분석_알림_정책.md` 3절의 정상 관측 최소 7일·유효 사용 최소 5일을 따른다. 초기 기준 initial_ready 및 기존 판단 가능 조건 decision_ready를 별도로 공개했다. 초기 판단과 기존 판단·알림 시각 조건을 제거하거나 변경하지 않았다.
- `service/output.py`: 기존 collecting/insufficient/personalized 계약을 유지하고 초기 기준 설명용 initial_basis를 추가했다.
- 실험실 대시보드에 초기 시간으로 판단 중이며 개인 학습 완료가 아니라는 설명을 표시한다.
- 출력 계약과 `docs/개인화_사용패턴_모델.md`에 기존 정책과 표시·판단의 차이를 명시했다.

### 회귀 결과

`tests/test_personal_usage_model.py`에서 다음을 검증했다.

- 연결 8일·개방 0회: 개인화 미완료, 출력 insufficient, 복원 후 동일.
- 초기 설정+관측 3일·사용 2일: initial_ready=True, ready=False, collecting 및 초기 기준 설명. 복원 후 동일하며 초기 기준의 check_required 판단도 유지.
- 관측 8일·사용 2일: 개인화 미완료.
- 관측 8일·사용 5일: personalized, 복원 후 동일.

`tests/test_a06_internal_output.py`에서는 대시보드 템플릿을 렌더링하여 collecting의 초기 기준 설명과 personalized에서 설명 제거를 검증했다. 실제 HA 화면 캡처는 수행하지 않았다.
