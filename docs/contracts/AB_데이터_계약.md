# A–B 데이터 계약 설계서 — HA 수집 이후 분석 입력

작성일: 2026-10-02 · 형식 버전: `0.1.0` · 상태: 합의된 개발 기준, 실측·통합 검증 전

## 1. 협업 경계

**A는 관측의 의미와 HA까지의 노출을, B는 HA 수집·정규화·저장 이후를 담당한다.** 이 계약은 B가 하드웨어 없이 가상 입력으로 개발하고, 이후 실제 입력으로 교체할 수 있도록 한다. 이 문서는 현재 개발 기준이며 하드웨어 지원 완료를 뜻하지 않는다.

```text
A: 센서 → 보드 관측·Edge AI → Matter → HA 엔티티/확장 정보
                                                ↓
B: HA 수집·변환 → 이 계약의 관측 기록 → 행동 묶음 → 개인 분석
                                                ↓
                          알림 정책 → HA → 자녀의 Companion 앱
```

보드에는 이 JSON을 전송하는 별도 프로토콜을 요구하지 않는다. 정규화 기록은 B 서비스 내부 전달·저장·재생에 사용한다. 저장소 종류나 HTTP/MQTT 서버를 추가로 확정하지 않는다. [보드 출력 설계서](../planning/보드_출력과_상태_추정.md)과 [서비스 요구](../planning/기능_입출력_정의서.md)를 함께 읽는다.

## 2. A가 제공할 매핑 정보

| 항목 | 인계 내용 |
|---|---|
| 논리 식별자 | household_id, device_id와 실제 장치의 대응. 서비스 재시작에도 유지 |
| 장치별 신호 목록 | 아래 signal별 제공 여부, 의미, 실제 HA entity_id 또는 확장 접근 경로 |
| 변환 | 열림 극성, 온도 단위, LED/운전 상태 값 매핑, 오류 표현 |
| 설치·버전 | 온도 측정 위치, 센서 보정 버전, 펌웨어/모델/SDK/HA 버전 |
| 보고 특성 | 실제 설정된 보고 주기·변화 보고, 연결 판정 방법, 알려진 누락 한계 |

가정의 실명·주소를 ID에 넣지 않는다. entity_id는 설정 파일에서 매핑하며 코드에 예시 이름을 고정하지 않는다. 지원하지 않는 신호도 목록에 남겨 ‘미지원’과 ‘일시 오류’를 구분한다. 보조 기기 미설치는 매핑 목록에 장치가 없는 것으로 표현한다.

## 3. 관측 기록 형식

UTF-8 JSON, 한 기록에 한 신호를 담는다. 파일 교환은 JSONL(한 줄 한 객체)을 제안한다. 아래 필드는 모두 존재하며, 허용된 곳에서 null을 쓴다. 수치 문자열이나 NaN은 쓰지 않는다.

| 필드 | 타입 | 의미 |
|---|---|---|
| schema_version | string | 현재 `0.1.0` |
| record_id | string | 수집기가 부여한 고유 ID. 같은 기록의 재전달·재생에서는 유지 |
| household_id / device_id | string | 설치 가정 / 물리 장치의 안정적인 논리 ID |
| stream_id | string | B 수집기의 연속 수집 구간 ID. 시작·재접속·관측 공백 발생 시 새로 부여 |
| sequence | integer ≥ 0 | stream_id 안에서 기록 생성 순서. 보드 패킷 번호가 아님 |
| mode | string | `live` / `simulation` / `replay` |
| kind | string | `snapshot` / `change` / `quality` |
| signal | string | 4절에 정의된 이름 |
| value | 신호별 타입 또는 null | quality가 good일 때 신호 값, 나머지는 null |
| quality | string | `good` / `unknown` / `unavailable` / `error` / `unsupported` / `stale` |
| observed_at | string 또는 null | 출처가 제공한 실제 측정 시각. 보드 시각을 알 수 없으면 null |
| source_at | string 또는 null | HA 상태의 last_updated 등 출처 기록 시각. 측정 시각과 다름 |
| received_at | string | 수집기가 이 기록을 만든 시각 |
| source_ref | string 또는 null | 실제 HA entity_id 또는 정의된 확장 경로. 가상 입력이면 null 허용 |
| inference | object 또는 null | 추정 신호의 방법·버전 정보. 직접 관측은 null |

시각 문자열은 UTC RFC 3339의 `Z` 형식으로 통일한다. 사용자 시간대는 별도 가정 설정 `Asia/Seoul`로 관리해 요일·식사 시간·방해금지를 계산한다. 한 레코드의 sequence만으로 다른 stream이나 다른 장치의 시간 순서를 비교하지 않는다.

`inference` 객체는 `method`(`edge_model` 또는 `rule`), `version`(string), `score`(0~1 또는 null)를 갖는다. score는 선택된 상태에 대한 모델 내부 점수이며 정확도·섭취 확률이 아니다. 추정 기능 미지원 시 inference=null을 허용한다. 방법/버전을 모르는 값을 확인된 Edge AI 출력으로 표시하지 않는다.

## 4. 신호 사전

| signal | good일 때 value | 생산 주체 / 의미 |
|---|---|---|
| lid_open | boolean | A. true=실제 뚜껑 열림 |
| lock_led / warm_led / white_rice_led / timer_first_led | `on` / `off` / `blinking` | A. 해당 LED의 관측 상태 |
| surface_temperature_c | number | A. NTC 설치 지점의 섭씨 온도 |
| cooker_phase | `cooking` / `warming` / `inactive` | A. 보드 추정. inference 필수 |
| device_connection | `online` / `offline` / `unknown` | B 수집기가 출처의 연결 정보를 정규화. 개별 센서의 정상 여부와 별개 |
| entrance_open | boolean | 선택적 현관 접촉 센서. true=열림, 이동 방향 아님 |
| motion_detected | boolean | 선택적 움직임 센서의 보고 상태. false=센서 보고상 미감지, 부재 확정 아님 |
| appliance_on | boolean | 선택적 가전·조명의 보고 상태. 켜져 있다는 것만으로 최근 사람이 사용했다고 단정하지 않음 |

같은 종류의 보조 기기가 여러 개면 device_id로 구분한다. 스위치 명령을 보냈다는 사실을 실제 동작 관측으로 변환하지 않는다. `device_connection=offline`은 연결 정보를 정상적으로 관측했다면 quality=good이며, 해당 센서 신호들은 별도로 unavailable 처리한다.

예약 시간, 실제 식사 수, 정확한 남은 밥의 양, 안전 여부는 이 계약의 관측 신호가 아니다. 보드 입력 ADC 원시값은 별도 학습 기록이며 단위를 lux로 가장하지 않는다.

## 5. 품질과 시각의 해석

| quality | 사용 방식 |
|---|---|
| good | 출처가 유효한 값으로 보고함. 최신 실측·정답·연속 관측을 보장하는 표시는 아님 |
| unknown | 장치는 있지만 의미 있는 값/판단을 얻지 못함 |
| unavailable | 기기 또는 수집 경로가 끊겨 현재 값을 사용할 수 없음 |
| error | 확인된 센서/해석 오류. 단절과 구별 |
| unsupported | 이 버전에서 신호를 제공하지 않음 |
| stale | 정해진 신호별 유효 기간과 확인 근거에 따라 현재 판단에 쓰기 어려운 값 |

HA의 unknown/unavailable을 false·0·inactive로 바꾸지 않는다. 마지막 정상 값은 이력에 보존하되, 현재 사용할 수 없는 신호의 value에는 되살려 넣지 않는다.

**HA의 마지막 상태 갱신 시각은 보드 측정 시각이 아니다.** 오래 닫힌 접촉 센서는 last_updated가 오래되어도 정상일 수 있다. 반대로 get_states로 캐시 값을 다시 읽었다고 새 실측이 생긴 것도 아니다. 센서별 보고/연결 확인 방법을 정하기 전에는 일괄 ‘N분 지나면 stale’ 규칙을 만들지 않는다. device_connection=online도 센서별 동작 정상이나 과거 기록 무누락을 보증하지 않는다.

observed_at이 없으면 source_at을 ‘HA가 기록한 시각’으로 분석에 사용할 수 있다. source_at도 없으면 received_at을 수집 시각의 근사로 사용하되, 실제 행동 시각을 안다고 표시하지 않는다. 재생 시 원래 세 시각을 유지하고 재생 실행 시각은 별도 실행 로그에 남긴다.

## 6. HA 수집 제안과 변화 처리

기본 수집 경로는 HA WebSocket API의 초기 상태 조회와 `state_changed` 구독이다. API는 인증·get_states·이벤트 구독을 제공한다. 실제 엔티티 매핑은 A의 인계를 따른다. [HA WebSocket API](https://developers.home-assistant.io/docs/api/websocket/)

1. 구독을 설정하고 초기 조회 동안 들어오는 이벤트를 잠시 버퍼링한다. 초기 상태와 겹치는 이벤트를 출처 시각·상태·식별 정보로 조정해 이중 반영하거나 최신 상태를 과거 값으로 덮어쓰지 않는다.
2. 최초 상태와 재접속 상태는 snapshot으로 기록한다. 처음 읽은 열림=true만으로 새로운 개방 사건을 만들지 않는다.
3. 같은 연속 관측 구간에서 정상적인 닫힘→열림 변화가 확인된 경우 change로 남기고 사용 행동 후보를 만든다. 속성만 바뀐 HA 이벤트나 동일 값 재전달은 새 개방이 아니다.
4. unknown/unavailable 뒤의 정상 복구는 snapshot으로 기준을 다시 잡는다. 단절 중 열었다 닫았을 가능성을 배제하거나 개방 횟수를 만들어내지 않는다.
5. 연결 끊김이나 확인된 관측 공백을 기록하고 새 stream_id로 재개한다. 한 센서만 오류이면 해당 신호의 연속성을 끊고 나머지 정상 관측은 보존한다.

record_id는 정규화 시 한 번 부여해 저장하고 재전달에서는 유지한다. HA 동일 이벤트 중복 유입은 정규화 전 entity_id·출처 시각·상태/속성·가능한 이벤트 식별자를 함께 비교한다. context ID 하나만으로 모든 이벤트를 동일 취급하지 않는다. 순서가 뒤늦은 기록은 이력에 남길 수 있지만 현재 상태를 과거로 되돌리거나 알림을 재발송하지 않는다.

sequence 누락은 정규화 기록 전달의 공백을 찾는 보조 수단이다. 보드→HA에서 발생한 미관측까지 감지하지 못한다. 빠른 개폐의 보존은 Matter 보고/이벤트 지원과 실제 연동 시험으로 확인할 항목이다.

## 7. Matter → HA → 계약의 변환 경계

| 항목 | 적용 원칙 |
|---|---|
| 개폐 | Contact Sensor / Boolean State 후보. HA가 이미 open 의미로 변환한 값은 다시 반전하지 않음 |
| 온도 | Temperature Measurement 후보. HA 엔티티의 실제 단위를 확인하고 섭씨로 정규화. raw Matter 값을 직접 읽는 경로와 변환을 섞지 않음 |
| LED·cooker_phase | 표준 의미에 맞는 매핑부터 검토. 아직 HA 엔티티가 존재한다고 가정하지 않음 |
| 확장 정보 | A가 HA 노출 경로를 제공하고 B가 정규화. 미구현이면 unsupported |

HA의 현재 Matter 구현은 Contact Sensor의 Boolean State 값을 반전해 HA의 문 열림 의미로 처리한다. 이것은 변환 중복을 피하기 위한 참고이며, 배포할 버전과 실제 열림·닫힘으로 확인한다. [HA Matter binary sensor 구현](https://github.com/home-assistant/core/blob/dev/homeassistant/components/matter/binary_sensor.py)

개폐·온도 외 항목은 클러스터/attribute ID를 임의로 확정하지 않는다. 매핑 검토가 남았다는 이유로 관측과 추정의 의미까지 미루지는 않으며, 가상 입력과 실제 지원 여부를 명시적으로 구분한다.

## 8. B의 분석·알림 경계

정규화 기록 이후 B가 만드는 정보는 다음과 같다. 이 절은 내부 책임과 의미를 정하며 B→HA의 최종 엔티티·서비스 규격까지 확정하지 않는다.

| 결과 | 필수 의미 |
|---|---|
| 사용 행동 묶음 | 시작/종료 시각, 근거 record_id 목록, 사용한 규칙 버전. 실제 한 끼라고 이름 붙이지 않음 |
| 개인 패턴 판단 | 평가 시각, 예상 사용 지연/긴 공백/점진적 감소, 근거, 학습 상태, 사용 가능한 관측 범위 |
| 알림 결정 | 발송/보류/해소, 사유, 연관된 공백 또는 추세의 ID, 다음 평가 시점 |
| 폰 화면 결과 | 최근 사용, 평소 대비 변화, 근거 이력, 연결/센서/학습 상태를 별도 표시 |

행동 묶음은 첫 개방부터 60분 고정 창, 규칙적인 사용의 첫 공백 안내는 두 예상 사용 창의 연속 미관측으로 합의했다. 실제 두 끼를 거른 것으로 해석하지 않는다. 감소 임계값과 세부 지연 수치는 정책 문서의 평가용 후보를 따른다. B가 구현할 때 조정 가능한 정책 설정으로 둔다.

관측 공백을 미사용 시간으로 그대로 누적해 생활 이상을 확정하지 않는다. 보조 정보가 없으면 해당 근거만 제외한다. 야간 취사나 timer_first_led 하나만으로 즉시 식사를 기대하지 않는다. 약 일주일은 초기 학습 목표 구간이며, 기록 부족과 연결 상태는 독립적으로 관리한다.

알림 결정과 실제 발송 결과는 별도로 저장한다. 재전달·재시작에도 같은 판단으로 중복 발송하지 않도록 결정 ID를 유지한다. 네트워크 실패로 발송 결과가 불명확한 경우 무조건 즉시 재전송하지 않도록 정책을 둔다. HA 호출 성공은 휴대폰 수신 확인과 동일하지 않다. 실제 폰 푸시와 외부망 상세 화면 확인은 통합 완료 조건이다.

simulation/replay는 실제 보호자 푸시 경로와 개인 학습 저장소를 기본적으로 분리한다. 가상 시험 결과를 실제 생활 기록에 섞지 않는다. replay는 원 기록의 record_id·시각을 유지하고 mode만 replay로 바꾸며, 별도 실행 ID의 저장 영역에서 처리한다.

## 9. 함께 제공하는 가상 기록과 검토 시나리오

[가상 관측 예시 JSONL](examples/observations.simulation.jsonl)은 형식 설명용이다. 실제 측정·AI 성능·확정된 주기를 나타내지 않는다.

| 예시 흐름 | 기대 처리 |
|---|---|
| 최초 닫힘 → 열림 → 닫힘 → 다시 열림 | 두 개방 기록 보존. 같은 행동으로 묶을지는 별도 시간 설정에 따름 |
| 온도·보드 상태 추정 | 관측 온도와 추정을 구분. 모델 버전 보존 |
| 시간 LED 꺼짐 | 예약 없음으로 변환하지 않음 |
| 장치 offline / lid unavailable | 생활 미사용 증거로 계산하지 않음 |
| 복구 snapshot이 열림 | 새 개방으로 집계하지 않음 |
| LED 센서 오류 | 다른 정상 신호와 분리 |
| 동일 record_id 재전달 | 저장/행동/알림 중복 방지 |

별도 시나리오로 방해금지 중 해소 시 미사용·재개 알림 취소, 실제 안내 후 재개 알림, 보조 기기 단절, 며칠간 감소와 단발 사용을 확인한다. 이들은 정책 시나리오이며 첨부 짧은 JSONL만으로 검증된 것은 아니다.

## 10. 인계 순서와 변경 규칙

1. B는 이 형식과 예시로 기록 읽기·품질 처리·행동 묶기부터 작성할 수 있다.
2. A는 신호별 실제 제공 경로와 지원 여부를 매핑표에 채운다. 미지원 신호는 정직하게 남긴다.
3. B는 가상 입력 대신 HA 수집기 출력을 같은 형식으로 연결한다.
4. A의 실제 기록으로 극성·단위·단절·재연결·빠른 개폐를 확인하고 예시와 차이를 반영한다.

계약의 의미·필수 필드가 바뀌면 데이터 형식 버전을 올리고 예시도 함께 수정한다. 알 수 없는 계약 버전이나 signal은 정상 신호처럼 해석하지 않고 별도 기록·오류로 남긴다. 하드웨어/HA 매핑 확인과 알림 민감도 선정은 다음 작업이며, 지금 이 문서를 읽기 위해 사용자의 추가 인터뷰는 필요하지 않다.
