## 2 개폐 기록 보존 범위

기존 SnapshotPacked v1과 원시 이벤트 형식은 유지한다. 추가 속성은
`1/4294048769/4293984261`, 최대 892바이트다. 최근 8개 **보고**가 한도이며
주기 보고도 슬롯을 차지한다. 기본 수신 설정은 기존 방식이고, 새 앱과 A/B 수신
코드를 설치한 후 A05 YAML에 `snapshot_history: true`를 명시해야 활성화된다.

- 같은 boot의 정상 폴링에서 보관된 중간 보고를 순서대로 기록한다.
- 같은 보고를 다시 읽어도 중복 기록·행동으로 재생하지 않는다.
- live 소비자의 첫 수신·재시작·확인된 offline 뒤와 보드 재부팅은 최신값을 기준 상태로 잡는다.
  명시적으로 실행 중인 B 개발 시험은 같은 boot의 보존된 이력을 재수신할 수 있다.
- 버퍼 초과는 순번 공백으로 남기고 누락된 사건을 만들어 채우지 않는다.
- 불완전·역순·혼합 출처·잘못된 이력은 거부한다. 이력 읽기 실패를 최신값 모드로 조용히 대체하지 않는다.
- test 보고는 기존처럼 live 학습 경로에서 거부한다. 개발용 연결 시험은 명시적으로 시작한 실행에만 사용한다.

사건 시각은 읽기 시각과 보드 uptime 차이로 추정하며 실제 수신 시각을 별도로
보존한다. 정밀한 UTC 동기화나 무제한 단절 복원은 제공하지 않는다. 1초 개폐도
계약 원시 기록에는 남지만 B의 기존 2초 debounce 때문에 최종 행동으로 세지
않을 수 있다. 실제 개방 보존과 흔들림 제거 기준은 현장 조작으로 함께 검증한다.

### 6.1 시험 중 발견해 수정한 진단 문제

HA 수신기는 읽기 오류 때 마지막 정상 순번을 지우고 있었다. 이 상태에서는
연결 복구를 처음 수신으로 취급해 누락/재부팅 진단이 사라질 수 있었다.
마지막 **검증된** 순번을 유지하도록 고쳤다. 읽기 실패 중 엔티티는 여전히
`unavailable`이며, 잘못된 데이터는 소비하지 않는다. 복구 시 순번을 대조하고
`last_gap`에 boot, 처음/마지막 누락 순번, 누락 보고 수를 남긴다.
최근 누락 정보는 이후 정상 읽기에도 보존되는 진단 이력이다.

새 수신기 SHA-256:
`f5b8c52c8adbd865707b49457c73c90e710c9c9143bd28b9c740b9103cd204e3`.
이전 수신기 백업: `/homeassistant/a05-sensor-before-gap-fix.py.bak`.
업로드 후 파일 해시 대조·Python 컴파일 검사, HA 구성 검사와 재시작을 완료했다.

### 6.2 보존 및 누락의 실제 의미

- 보드 저장 한도는 개폐 8회가 아니라 **주기 보고를 포함한 최근 보고 8개**다.
- 단절 시험 실행 ID: `8308d4c3d9094aa8857f45e5f01348ca`.
  B 기록 `61a183d63ae54e52aba732e1c4cead29:8`(159 닫힘), `:15`(160 열림).
  이 시험은 서버 재기동까지 포함되어 앞쪽 주기 보고 일부는 이미 유실됐다.
  따라서 단절 전체 무손실이 아니라 **보존된 버튼 한 쌍 복구**의 증거다.
- 초과 시험 실행 ID: `26779c641eff48f28276e1f79bdbe008`.
  B JSONL에 이전 stream의 `lid_open: unavailable`과 `device_connection: offline`,
  새 stream `7f3f12b594d441c69ef1ab55b3c8b6a5`의 `:1`(17 닫힘), `:8`(18 열림)을 확인했다.
  유실된 5~16번을 생성하지 않았다. B 연결 시험은 첫 닫힘→열림 성공 후 기록을 멈추므로
  이 결과를 마지막 버튼 14개가 모두 B에 남았다는 뜻으로 해석하지 않는다.

  사용자가 휴대폰 실수신까지 확인했다. 후속 시험의 알림은 HA 호출 수락까지만 확인했다.
- HA는 기존 Matter node 4로 다시 수신 중이다. 비활성화 상태를 남기지 않았다.

## 7 느린 점멸 보완과 검증 — 2026-10-06

4번의 센서 없이 가능한 구현·PC 평가·실제 보드 실행을 완료했다.
실제 밥솥 LED의 주기·밝기·의미를 측정한 검증은 아니며, 센서 입고 뒤 최종 기준을 확정한다.

### 7.1 변경 내용과 동작 비용

전처리 `a07-preprocess-v3`는 기존 2초 모델 특징과 모델 가중치를 유지하면서,
LED 판정에 최근 400개 관측(20 Hz 기준 약 20초)을 추가로 사용한다.
온전한 창에서 전환이 없으면 점등/소등, 3개 이상이면 반복 점멸,
1~2개이면 전환 중 `unknown`으로 처리한다. 단일 펄스를 반복 점멸로 확정하지 않는다.
채널 품질이나 연결이 불완전하면 확정하지 않는다. 모든 LED 상태가 확정되고
보온 LED가 점멸이 아닐 때만 기존 모델의 판단을 허용한다.
따라서 2초 특징이 점등처럼 보여도 긴 이력에서 보온 LED 점멸이 확인되면 판단을 막는다.

상태가 바뀌거나 채널 오류에서 회복한 뒤 확정에는 새 20초 관측 창과 최대 2초의
출력 대기가 필요하다. 고정 시험의 켜짐↔꺼짐 확정 지연은 양방향 모두 19.95초였다.
온도·접점은 독립적으로 관측하며, 통신 공백 뒤 모델의 기존 60초 연속 이력 조건도 유지한다.
원시 입력 계약, HA/B 수신 형식, 모델의 11개 특징은 변경하지 않았다.

### 7.2 PC 평가

기존 모델을 재학습하지 않고, 동일한 합성 입력과 특징에서 이전 유효성 조건과 새 조건을 비교했다.
각 파형은 180초, 온도는 55°C이며 보온 LED만 점멸한다. 모델 판단 창은 파형당 61개다.

| 평가 | 사례/판단 창 | 기존 보온 오판 | 개선 후 보온 오판 | 결과 |
|---|---|---|---|---|
| 기존 점검의 반례: 0.15 Hz, 켜짐 50%, 위상 0 | 1 / 61 | 18 | 0 | 모든 창에서 점멸 확인 |
| 후보 범위: 0.1~2 Hz, 켜짐 10~90%, 3개 위상 | 54 / 3,294 | 473 | 0 | 모든 창에서 점멸 확인 |
| 별도 주기·비율·위상 조합 | 96 / 5,856 | 698 | 0 | 모든 창에서 점멸 확인 |
| 후보 밖: 0.025·0.05 Hz | 18 / 1,098 | 494 | 81 | 범위 밖 보장 불가 확인 |

첫 반례는 후보 범위 평가에 포함되므로 합산하지 않는다. 범위 안에서 오판이 0이라는 것은
합성 파형에서 보온 판단을 차단했다는 뜻이지 실센서 정확도 100%라는 뜻이 아니다.
매우 느리거나 샘플 사이에 끝나는 점멸, 첫 전환을 아직 관측하지 못한 상태는 구분에 한계가 있다.
실측 주기가 후보 범위를 벗어나면 창 길이·판정 기준을 다시 정해야 한다.

초기 평가 파일 `evaluation.json`에는 부동소수점 시간 경계 때문에 의도한 2 Hz 파형의
펄스가 일부 사라진 결과가 남아 있다. 입력 생성기를 정수/유리수 연산으로 고치고
전체를 재실행한 `evaluation-exact.json`을 위 표의 근거로 사용했다.
이 과정에서 모델을 재학습하거나 판정 임계값을 평가 결과에 맞춰 바꾸지 않았다.

## 8 제품 펌웨어 경로 통합 — 2026-10-06

사용자의 제품 펌웨어 통합 요청에 따라 `firmware/a08/`에 재현 가능한 제품 앱 구성을
추가했다. SDK를 복사해 저장하지 않고 기존 A05 앱 생성기에 제품 코드를 적용한다.
[제품 앱 안내](../../firmware/a08/README.md)에 생성·빌드·보정·검증 방법을 기록했다.

### 8.1 통합 범위

ADC 5채널 및 GPIO 접점 → 전처리 v3 → 기존 고정 모델 → SnapshotPacked 및
SnapshotHistory → 기존 Matter 전송 경로를 연결했다. 짧은 개폐는 모델의 60초 준비나
2초 결과 갱신을 기다리지 않고 50ms 안정 확인 뒤 이력에 남긴다. 정기 보고는 2초다.
생산자와 Matter 이벤트 루프 사이에는 mutex를 두어 스냅샷과 이력의 일관된 복사본을 전달한다.
전송 실패 중에도 최근 8개 보고는 남기고 다음 발행에서 다시 전달한다. 영구 저장은 아니다.

기존 관측 공백 초기화·보정값 검사·느린 점멸 판정도 같은 제품 경로에 연결했다.
ADC 원시값은 SDK 기준 전압으로 mV로 변환한 뒤 측정된 공급 전압 비율로 정규화하도록 구현했다.
현재 공급 전압과 실물 보정은 미확정이므로 `SENSORS_CONFIRMED=false`이다.
센서가 없는 핀의 읽기 값은 진단 로그에만 남기며 온도·LED·개폐·AI 정상값으로 사용하지 않는다.
출처는 계속 `test`이고 B의 live 학습·알림을 켜지 않았다.

### 8.2 실제 보드 검증과 발견한 문제

- 같은 Pipeline의 부팅 통합 검사: 모델 준비 전 짧은 개폐, 이력 보존/한도,
  관측 공백·boot 변경, 잘못된 보정, 느린 보온 LED 점멸 — 오류 0.
- 실제 ADC/GPIO 드라이버 초기화 오류 0, ADC 5채널 읽기 성공.
  센서가 미연결인 상태의 드라이버 동작 확인이며 전압·온도 정확도 검증은 아니다.
- 최종 이미지에서 200개 표본 단위의 **연속 11개 구간**이 최소 48ms/최대 52ms,
  관측 공백 0으로 통과했다. 약 110초의 20Hz 연속 취득을 확인했다.
- 미보정 상태에서 개폐·온도·LED·AI가 모두 unknown으로 유지되는 보고 60개,
  SnapshotPacked/History 발행 상태 모두 성공을 확인했다.
- 기존 A 도구 회귀 시험 35개 통과. 새 폴더에 생성한 핵심 파일 12개를 현재 빌드
  입력과 대조했다. `prj.conf`의 빈 줄 하나를 제외하고 일치한다.

초기 빌드의 ADC 입력 상수는 SDK 3.4.1의 `NRF_SAADC_AIN*` API에 맞게 수정했다.
첫 실기에서는 개별 ADC 읽기와 낮은 취득 우선순위, SDK의 동기식 UART 상세 로그가
관측 간격을 흔드는 문제가 드러났다. ADC 5채널 일괄 읽기, 취득 우선순위 조정,
