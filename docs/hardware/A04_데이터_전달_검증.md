# A04 표준·확장 데이터 전달 검증

2026-10-04 · 전달 경로 기술 검증 완료(추가 검증 범위는 판정표 참조) · 브랜치 `a/environment-matter-validation`

## 현재 확인한 범위

| 항목 | 결과 | 근거/남은 검증 |
|---|---|---|
| 표준 개폐 | HA 표시와 상태 변화 확인 | A03 버튼 누름/해제, A04 원시 속성 확인 |
| 표준 온도 | HA 실수신 확인 | endpoint 2 원시 2100/2150 → HA 21.0/21.5°C |
| 제조사 확장 | 서버 원시 속성 확인 | NordicDevKit 확장의 ReportCounter=2 표시 |
| 보고 카운터 | HA 숫자 엔티티 생성 확인 | `sensor.a04_board_report_counter` 실제 읽기 값 14 |
| 단절·복구 | CPU 정지·재시작 시험 성공 | HA 14→unavailable→1→2; 장시간/물리 전원 단절은 미검증 |

실제 센서는 아직 없다. 버튼은 시험 입력이며 온도·카운터도 전달 시험용이다. 이 기록을 밥솥 측정 또는 AI 검증으로 사용하지 않는다.

## 확장 표현 검토

- 온도는 TemperatureMeasurement(`0x0402`)의 MeasuredValue(`0`)를 사용한다. 원시 단위는 0.01°C이며 HA는 °C로 표시한다.
- 펌웨어 버전은 BasicInformation의 표준 버전 필드를 사용한다. 모델 버전·추론 방법·점멸·판단 불가는 펌웨어 버전과 별도다.
- LED 점멸/unknown과 취사 상태 추정을 조명 제어 명령으로 위장하지 않는다. 제조사 확장 읽기/구독 경로가 후보이며, HA 자동 엔티티 생성을 보장하지 않는다.
- 새 연동 명세의 보고 카운터는 보드에서 증가해야 한다. HA uptime의 부팅 시각이나 수신기가 만든 시각을 카운터 대신 사용하지 않는다.
- SDK의 NordicDevKit 예제를 기반으로 한 아래 ID는 **개발 시험 전용**이다. 제품용 공개 클러스터 계약을 확정한 것이 아니다.

## 시험용 복사본

`tools/prepare_a04_probe.py`는 SDK contact_sensor를 새 디렉터리로 복사하고 온도 엔드포인트와 읽기 전용 NordicDevKit 확장을 더한다. `firmware/`와 SDK 샘플 원본은 수정하지 않는다.

| 경로 | 시험 의미 |
|---|---|
| `1/69/0` | 기존 버튼 접촉 상태 |
| `2/1026/0` | 20~25°C 합성 온도; 원시 2000~2500 |
| `1/0xFFF1FC01/0xFFF10002` | 시험 버튼 상태 |
| `1/0xFFF1FC01/0xFFF10003` | uint32 ReportCounter; 부팅 후 10초, 이후 60초마다 증가 |

카운터는 재부팅 시 0으로 돌아간다. 이는 전송 시험이며 BootId·동일 관측 snapshot·영구 순번 구현을 대체하지 않는다. 카운터 감소 시 B가 관측 연속성을 끊는 계약을 유지한다.

생성 예:

```powershell
. ./local-data/a03/sdk-env.ps1
python ./tools/prepare_a04_probe.py --sdk C:/ncs/v3.4.1 --output ./local-data/a04/probe
# 아래 west 명령은 C:/ncs/v3.4.1 작업 디렉터리에서 실행한다.
west zap-generate --full -z <probe>/src/default_zap/contact_sensor.zap -j <probe>/src/default_zap/zcl.json
```

준비 스크립트는 기존 출력 디렉터리를 덮어쓰지 않는다. 생성/빌드 로그는 `local-data/a04/`에 보관한다. 빌드 성공·플래시·HA 수신은 각각 실행 증거를 확인한 뒤 이 문서에 추가한다.

### 실행 중간 기록

- ZAP `2025.10.23-nightly` 설치 및 전체 데이터 모델 생성 성공. Windows에서 복사본의 ZCL 참조를 상대 경로로 지정해야 했으며 준비 스크립트에 반영했다.
- 첫 링크에서 NordicDevKit 속성 접근 함수가 누락됐다. `CHIP_APP_ZAP_DIR`를 `data_model.cmake`보다 먼저 설정하도록 준비 스크립트에 반영했고, 수정 후 전체 sysbuild가 성공했다(`build-retry.log`, 종료 코드 0).
- 최종 앱 사용량: FLASH 754712 B / 1949552 B, RAM 172636 B / 511 KiB. 서명된 앱 HEX 주소 범위 `[0xd000, 0xc54e8)`를 검사해 factory-data/storage와 겹치지 않음을 확인했다.
- 최종 A04 앱 HEX SHA-256: `A1F17112EF9DD84CDD65CA7FFCB9D12A1453449A372FE5F7C96C819443B35E4D`. 표시 버전 `3.4.1+0`은 기본 예제와 같으므로 이 해시와 `A04 TEST` 로그로 시험 빌드를 구별한다.
- 플래시 dry-run에서 `--domain probe`, `chip_erase_mode=ERASE_NONE`, `verify=VERIFY_READ`와 앱 HEX만 사용하는 것을 확인했다. dry-run 출력의 “flashed successfully”는 실제 기록 성공 증거로 사용하지 않는다.
- 생성된 모델에 endpoint 0/1/2, BooleanState·TemperatureMeasurement·NordicDevKit, uint32 ReportCounter가 포함됨을 확인했다. 확장 제어 명령은 제거했다.
- SDK toolchain Python으로 준비/수신 코드 문법과 생성 모델의 엔드포인트·속성 조건을 확인했다. HA 수신 코드 실행 검증을 대신하지 않는다.
- `local-data/a04/pairing-storage-backup.hex`: 기존 storage 파티션 `0x1f1000`, 길이 `0xc000`의 로컬 백업. 등록 정보가 포함될 수 있으므로 Git/공유 문서에 첨부하지 않는다.
- HA 공식 File editor 6.1.0 설치·기동 확인. 시험용 통합 코드 설치 여부는 아래 실제 수신 기록에서 별도로 관리한다.
- 온도 endpoint 2의 Identify 인스턴스 초기화 누락을 수정했다. `build-identify-fix.log`, `flash-identify-fix.log` 성공, `final-boot.log`에서 Thread attached·2개 구독 복원·카운터 1→2와 온도 2050→2100, 상태 코드 0/0을 확인했다.
- 시험용 HA 읽기 코드 `tools/a04_ha_probe/`를 `/homeassistant/custom_components/bapsim_matter_probe/`에 설치했다. 기존 Matter 클라이언트로 30초마다 명시적 읽기를 수행한다. 카운터를 수신기에서 생성하지 않으며 push 구독 성공을 뜻하지 않는다.
- 기존 `configuration.yaml`은 `local-data/a04/configuration.before-a04.yaml`로 백업한 뒤 예제 sensor 블록만 추가했다. 첫 구성 검사에는 새 통합을 찾지 못하는 경고가 있었으나, Core 재시작 후 숫자 엔티티가 생성되어 14를 읽었다. 편집기에 붙여넣은 Python/YAML은 클립보드 내용과 로컬 원본을 대조한 뒤 저장했다.

### 실행 판정표

| 시험 | 성공 기준 | 상태 |
|---|---|---|
| 개폐 기본 경로 | 버튼 누름/해제와 HA 닫힘/열림 대응 | A03 성공, A04 확장 이미지에서는 재확인 필요 |
| 표준 온도 | endpoint 2의 원시값/100과 HA °C 일치, 두 값 이상 갱신 | 성공: 21.0→21.5°C (`ha-temperature-21-5.jpg`) |
| 서버 확장 | 실제 보드의 ReportCounter를 서버에서 읽기 | 성공: 값 2 (`server-counter-2.jpg`), 증가 로그 1→2 |
| HA 확장 | 같은 보드 카운터를 HA 숫자 엔티티로 확인 | 성공: 최초 14, 재시작 후 1→2 증가 |
| 구독과 폴링 구분 | 성공한 수신 방식과 미검증 범위를 구분 | 보드 2구독 복원 로그, HA 확장 30초 명시적 읽기. 확장의 push 알림 주기는 미검증 |
| 재시작 | 등록 유지, 카운터 초기화와 다시 증가 확인 | 최종 이미지 부팅에서 2구독 복원·1→2 확인 |
| 단절 | 정상값 캐시와 현재 읽기 실패/unavailable을 구분 | CPU halt 후 HA 14→unavailable (17:10:47), 물리 전원 차단 시험은 아님 |

단절 후 디버거 reset으로 복구했다. 17:11:27 HA 값 1로 복귀해 기록상 unavailable 기간은 약 40초였으며 이후 2를 확인했다. 이 수치는 해당 시험 관측값이며 일반적인 탐지 시간 보장이 아니다. `recovery.log`에는 Thread attached, 2구독 복원, counter 1→2가 기록됐다. 최종 HA 구성 검사는 경고 없이 통과했다. 새 이미지에서 버튼을 직접 누르고 해제하는 반복 시험은 아직 미실행이며 A03 결과와 구분한다.

복구용 기존 이미지: `local-data/a04/a03-rollback.signed.hex` (SHA-256 `650DDF2F40BACE03AD9DB5B194FAAAD2A0F4B181B7BA518AFE00D0FD0E834FF6`). factory-data와 storage를 덮어쓰는 전체 삭제/복구 명령은 이 시험의 플래시 절차에 사용하지 않는다.

## B 인계 양식

신호별로 아래 항목을 채우고 `미검증`을 추정값으로 덮어쓰지 않는다.

```yaml
signal: lid_open
input_kind: test
device_id: 9f38f5d8ba55b2afe91ea0a44d6fa56d
node_id: 4
endpoint: 1
cluster: 69
attribute_or_event: attribute/0
ha_entity_or_extension_path: binary_sensor.matter_contact_sensor_mun
value_mapping: "HA on=true, off=false; raw Matter StateValue는 반대 극성"
unit: null
quality_mapping: "unknown/unavailable 보존; 실센서 품질 미검증"
reports: "버튼 변화와 재부팅 복구 확인; 최대 보고 간격 미검증"
firmware_version: 3.4.1+0
sdk_version: 3.4.1
status: verified_test_input
```

HA 확장 카운터가 확인됐어도 아래 출처 검사 합의 전에는 B의 실시간 연결 근거 설정을 완료로 처리하지 않는다. A03/A04 전달 성공만으로 B의 생활 미사용 분석을 실기 검증했다고 표시하지 않는다.

### 온도·카운터 인계값

| 신호 | HA 엔티티 | 원시 경로 | 타입/단위 | 비고 |
|---|---|---|---|---|
| 시험 온도 | `sensor.matter_contact_sensor_ondo` | `2/1026/0` | Matter 정수 0.01°C → HA °C | HA 값을 다시 100으로 나누지 않음; revision 4, FeatureMap 0 |
| 보고 카운터 | `sensor.a04_board_report_counter` | `1/4294048769/4293984259` | uint32, 단위 없음 | platform `bapsim_matter_probe`; 30초 읽기, 20초 제한; 실패는 unavailable |

확장 클러스터는 서버에 이름 미상으로 표시되지만 정수 값은 디코딩됐다. 서버 UI의 확장 FeatureMap은 null로 표시되어 표준 모델처럼 해석됐다고 주장하지 않는다. 미지원 경로·비정수 응답은 코드에서 unavailable로 처리하지만 별도 오류 경로를 실기 주입하지는 않았다.

### 설치·복구 절차

1. `tools/a04_ha_probe/bapsim_matter_probe`의 세 파일을 HA 설정 폴더의 `custom_components/bapsim_matter_probe`에 복사한다.
2. `configuration.example.yaml`의 항목을 기존 sensor 목록에 합친다. 다른 설치에서는 Matter entry/node/path를 다시 확인한다.
3. 구성 검사 후 HA Core를 다시 시작하고 `sensor.a04_board_report_counter`의 실제 숫자를 확인한다. 이 시험 코드는 HA 2026.9.4 내부 Matter API에 의존하므로 업데이트 후 재검증한다.
4. 제거할 때는 추가한 sensor 항목만 빼고 Core를 재시작한다. 다른 변경이 없다면 로컬 `configuration.before-a04.yaml` 백업으로 복구할 수 있다. 시험 통합 파일은 비활성화 후 별도로 보관한다.
5. 보드 복구는 기존 앱 HEX를 앱 영역에만 기록한다. 전체 erase/recover를 사용하지 않으며 등록 정보를 보존한다.

### 최신 B 구현과의 경계

`service/ha_matter_inputs.py:is_matter_entity`는 엔티티 레지스트리의 `platform == "matter"`만 허용한다. 별도 A04 통합(`bapsim_matter_probe`)의 엔티티는 보드에서 Matter로 읽었어도 현재 B 검사에서 거부된다. 따라서 **보드→Matter Server→HA 시험 성공과 B 서비스 연결 성공을 구분**해야 한다.

인계 시 B와 합의할 항목은 검증된 확장 수신 통합의 출처 검증 방식이다. 수신 통합 이름, Matter 구성 항목/노드/속성 경로, 숫자 타입, 갱신·실패 결과를 제공한다. 기존 출처 검사를 임의로 해제하거나 시험 엔티티를 공식 `matter` 플랫폼인 것처럼 위장하지 않는다. B 코드 변경은 이 A04 시험 범위에 포함하지 않는다.
