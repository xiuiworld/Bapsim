# A 개인 실행계획 — 장치·보드 AI·Matter·현장 통합

작성·진행 상태 갱신: 2026-10-04. A는 현재 사용자, B는 원격 팀원이다. 사용자 확인과 [역할 분담](역할_분담.md)을 기준으로 작성했다. 체크된 항목은 실행 결과 또는 사용자 확인으로 완료한 일이며, 체크되지 않은 항목은 남은 일이다. 센서는 10월 6일 **발송 예정**이고 수령일·발표 마감일은 확정하지 않았다.

## 1. 목표와 담당 경계

A의 목표는 밥솥의 관측과 보드 상태 추정을 Matter로 HA까지 전달하고, B가 제공한 서비스를 현장에서 실행·검증하는 것이다.

```text
A: 센서 → 보드 관측·상태 추정 → Matter/Thread → Nest → HA 수신
                                                               ↓ 인계
B:                                      정규화·저장 → 개인 패턴 → 화면·알림
A+B:                                    현장 실행 → 실제 폰 시험 → 오류 분담
```

| 작업 | A가 할 일 | B에게 맡기거나 받을 것 |
|---|---|---|
| 개발환경 | Nordic 도구·보드, HA OS VM·Matter Server·네트워크 준비 | 서비스의 실행 요건 |
| 센서·보드 | 배선·부착·관측·보정·펌웨어·보드 AI | 필요 시 기록 분석 지원 |
| Matter | 표준 신호·확장 정보의 HA 수신, Multi-Admin | 수신 후 내부 이벤트 변환 |
| 데이터 | 보드 학습용 원시 로그·실제 조작 라벨·신호 매핑 | HA 이후 저장·보존·기록 재생 코드 |
| AI | 취사/보온 등 현재 운전 상태 추정 | 개인별 사용 패턴·장기 감소·확인 필요 판단 |
| 서비스 | 전달된 배포본 실행, 설정·접근 환경 제공 | 시뮬레이터·보조 정보·분석·화면·알림·응답 로직 |
| 휴대폰 | Companion 연결·외부 접속·현장 시험 | 화면·알림 설정과 서비스 오류 수정 |

A의 보드 학습용 합성 데이터 생성기는 B의 생활 패턴 시뮬레이터와 별개다. 기존 입력 어댑터에 AI를 넣지 않고 `inputs/base/contracts.py`의 원시 이벤트 경계를 유지한다. 이 계획 작성으로 공유 코드나 `firmware/`를 수정하지 않는다. 실제 구현은 해당 작업을 명시한 요청과 폴더 지침에 따라 진행한다.

## 2. 진행 원칙

- 센서·통신·AI를 한 번에 완성하려 하지 않는다. 시험 신호 연결부터 성공시킨다.
- AI 완성을 기다리지 않고 검증된 개폐·온도를 B에게 먼저 제공한다.
- 센서 도착 전 합성 데이터로 학습·변환·보드 실행 경로를 준비하고, 도착 후 실측으로 보정·평가한다.
- 실제 측정, 시험 입력, 합성 데이터, 규칙 추정, AI 추정을 구분한다.
- 완료 판단은 설치 여부가 아닌 로그와 재현 가능한 동작으로 한다.
- 기한은 마감일 확인 후 배정한다. 아래 순서와 완료 조건을 우선한다.

### A05. 합의된 데이터 모델 구현·HA 노출 — 진행 중

2026-10-04 계획 보완: 기존 계획은 A04의 시험값 전달 확인에서 A07의 AI 준비로 넘어가며, 공통 계약을 실제 전송·수신 코드로 구현하는 작업을 독립 실행 항목으로 누락했다. A10/A11의 출력·통합 확인만으로 이 구현을 대신하지 않는다. A04의 기술 확인 실적은 유지하되 이 단계는 별도로 완료해야 한다.

새 통신 계약을 처음부터 만들지 않는다. [Matter·HA 연동 명세](../contracts/Matter_HA_연동_명세.md)와 [A–B 데이터 계약](../contracts/AB_데이터_계약.md)을 기준으로 구현한다. 후자의 JSON은 B의 HA 수집 이후 기록이며 보드가 그대로 전송할 패킷이 아니다. `firmware/`는 폴더 지침에 따라 별도 명시 요청 없이 수정하지 않는다.

- [x] 공통 명세의 개폐·온도·LED 4종·운전 상태·신호별 품질·추정 방법/모델 버전/점수와 SchemaVersion·BootId·ObservationSequence·UptimeMs·보고 카운터를 구현 대응표로 정리. 제공/미지원/미구현을 구분한다([A05 구현 기록](../hardware/A05_데이터모델_구현.md)).
- [x] 선택 SDK에서 확장 ID·타입·null/enum 표현과 동일 시점 Snapshot 전달 방식을 구체화하고 버전·속성표로 기록(SnapshotPacked v1, 읽기 전용 단일 octet-string).
- [x] 센서 없이 계약에 맞춘 시험값을 보내는 장치 측 구현을 준비하고, 정상 전환·판단 불가·오류·미지원·재부팅/순번 초기화 입력을 재현한다(test origin 명시, 실제 AI/센서 아님).
- [x] 합의된 확장 항목을 HA에서 읽고 노출하는 수신 코드를 구현(공유 Snapshot에서 센서 15개, 품질·원시값·추정 버전 보존; 수신기 판단/값 생성 없음).
- [x] 온도 원시 단위·LED/상태 enum·품질·추정 버전과 Snapshot 일관성, 시험 15초 보고/HA 5초 읽기, CPU 정지 시 unavailable 및 재부팅 후 새 BootId/카운터 복구 확인.
- [x] 새 이미지 물리 버튼·빠른 반복 대조 완료. 단일 누름/놓기 2개 변화 모두 수신, 5회 반복은 10개 중 2개, 10회 반복은 20개 중 2개 HA 상태 변화로 기록. 실제 간격·누락 8/18개·gap 진단을 A05 실행 기록에 남겼다. 모든 개폐 이벤트 보존은 현재 5초 폴링으로 충족하지 못한다.
- [x] 실제 HA entity_id/확장 경로·변환 규격·재현 입력·기대 출력을 B 인계 자료로 작성(`tools/a05_contract/ha_mapping.test.json`, README, A05 실행 기록).
- [ ] B 담당 수집기의 확장 출처 검증·test/live 분리와 호환 경로를 확인하고 내부 계약까지 통합 시험. 현재 공식 `matter` 플랫폼만 받는 검사와 불일치한다. A가 출처 검사를 우회하거나 B 정규화·분석 로직을 중복 구현하지 않는다.

완료 조건: 합의된 각 항목의 제공 상태와 HA 접근 경로가 명확하고, 지원하는 항목은 계약에 맞춘 시험값으로 장치→Matter→HA 수신이 검증된다. B 인계 경로의 호환성까지 확인하며 막힌 항목은 완료로 체크하지 않는다. 실제 센서 대응과 AI 성능, 폰까지의 최종 통합은 A08~A12에서 별도 검증한다.

2026-10-04 진행: 전체 Snapshot 시험 앱을 빌드·플래시하고 HA 센서 15개로 실수신을 확인했다. 오프라인 8개 테스트와 실제 보드 바이트 디코드, 오류/미지원 표현, 정지/재시작 복구를 확인했다. 현재 A05 시험 이미지가 실행 중이며 실측/AI가 아니다. 물리 버튼 반복 시험까지 완료했다. B 호환성 검증이 남아 A05 전체는 진행 중이다.

진행 순서: A04 → **A05** → A07. A06 실행 환경은 B 배포 준비에 맞춰 병행한다. A07의 학습 준비는 병행할 수 있지만 데이터 모델 구현을 AI 완성이나 센서 도착 이후로 미루지 않는다.

### A06. B 서비스 연결을 위한 로컬 실행 환경 — 미착수

근거: 팀 합의 D04·D09·D12와 [출력 계약](../contracts/분석결과_HA_휴대폰_출력계약.md). A는 환경을 준비하고 B의 배포본을 실행한다. 분석·저장·MQTT discovery·화면·알림·명령 처리 코드는 B가 제공한다. A05/A07와 병행할 수 있고, 외부 접속은 사용자 요청대로 나중에 진행한다.

- [ ] B 배포본의 Docker 실행 요건·이미지 버전·설정/볼륨 예시·기동/중지/복원 절차를 받고 HA VM과 동시 실행할 자원을 확인한다.
- [ ] 로컬 MQTT 브로커의 실행 위치를 정하고 HA MQTT 통합 및 B 컨테이너와의 접속을 구성·검증한다. 보드의 Matter 경로는 유지한다.
- [ ] 실제 HA 주소·신호 매핑·논리 household_id/device_id·시간대·폰 알림 대상 서비스와 접근 설정을 준비한다. 계정 비밀은 Git·공유 로그에 넣지 않는다.
- [ ] B가 제공한 discovery/화면/결과 만료 설정을 설치하고, 시험 상태→MQTT→HA 화면의 반영 및 끊김 표시를 확인한다. A가 B의 출력 코드를 새로 만들지 않는다.
- [ ] 시험 입력과 실제 기록의 저장 위치·topic prefix·알림 대상을 분리한다. 시험 입력이 실제 개인 학습과 보호자 발송에 섞이지 않는지 B 설정으로 확인한다.
- [ ] 영속 볼륨·로그·백업/복원 경로를 구성하고, B의 관측90일/행동·기준·판단·발송180일 보존 설정을 적용한다. 보존·삭제 코드 작성은 B 담당이다.
- [ ] B의 개발용 시나리오로 표준 개폐→B 수집→시험 결과→HA→실제 폰의 첫 연결을 확인한다. 폰 수신과 클릭 후 상세 화면을 따로 기록하며 개인 패턴/AI 성능 검증으로 표시하지 않는다. 외부망 시험은 A11에서 별도 수행한다.

완료 조건: A의 환경에서 B 배포본이 HA 입력을 읽고 결과를 HA·폰에 전달하며 재시작 후 필요한 상태가 복원된다. B 배포본이 없으면 환경 준비까지만 기록하고 연결 성공으로 체크하지 않는다.

### A07. 보드 AI 준비 — 합성 데이터로 선행

## 6. 합성 데이터로 시간을 줄이는 구체적인 방법

### 가능한 것과 실측이 필요한 것

합성 데이터로 모델을 미리 학습할 수 있다. 다만 현재 밥솥의 부착 위치 온도, 광센서 주변광·반응, LED 의미와 전환 시점은 미측정이다. 합성만으로 학습한 모델의 실제 성능은 보장되지 않는다. 권장안은 **합성으로 개발 경로 완성 → 소량 실측으로 보정·재학습 → 별도 실측으로 평가**다.

| 센서 전에도 가능한 일 | 센서 후 확인해야 하는 일 |
|---|---|
| 시계열 형식·입력 창·전처리·학습 코드 | 실제 ADC 범위·온도 지연·센서 위치 영향 |
| 후보 모델 학습·내보내기·보드 실행 | 실제 상태 구분 가능성·누락·오분류 |
| 잡음·누락·시간 변동에 대한 모의 시험 | 실제 회차·조건에서의 성능 |
| Matter 시험값 전달 | 실측 상태와 전달값의 대응 |

### 데이터 생성 방법 제안

LLM에게 임의의 숫자 행을 대량 작성시키기보다, 가정과 난수 seed가 기록되는 시계열 생성기를 만든다.

1. 회차별 운전 단계와 지속 시간을 생성한다. 이것을 합성 정답으로 둔다.
2. 단계에 따른 온도 상승·유지·냉각, 센서 지연, LED 변화를 가정해 신호를 생성한다. 이는 실제 모델의 측정 특성이 아니라 검증 전 가정이다.
3. 초기 온도·시간 길이·광량·잡음·센서 오프셋·일시 누락을 여러 범위로 바꾼다. 서로 불가능한 조합을 무작위로 섞지 않는다.
4. 상태 경계와 모호한 신호도 포함하고 필요한 입력이 없으면 판단 불가로 처리한다.
5. 실측 후 관측된 범위로 생성기를 수정하고, 학습용 실측에 한해 타당한 잡음·시간 변형 증강을 추가한다.

단순히 `온도 > X면 cooking`으로 라벨을 만든 뒤 모델이 같은 규칙을 복원한 결과를 독립 정확도로 주장하지 않는다. 합성 성능은 생성한 가정 안에서의 성능이다. 노이즈·시간 변형으로 라벨 의미가 바뀌는 증강은 사용하지 않는다.

### 데이터 부족을 다루는 평가 원칙

- 회차 단위로 학습/개발/최종 평가를 나누고, 그 이후에 윈도우 분할·증강한다.
- 같은 원본 회차의 증강본을 평가 세트에 넣지 않는다.
- 최종 평가 회차로 센서 보정·생성기·임계값을 조정했다면 더 이상 독립 최종 평가가 아니다. 새 회차를 확보한다.
- 합성 데이터 양·혼합 비율은 고정 정답이 없다. 개발용 실측으로 선택하고 합성이 해로우면 줄이거나 제외한다.
- 실측이 매우 적으면 복잡한 모델보다 규칙 기준선과 작은 모델을 먼저 비교한다.
- 실측 부족으로 AI를 검증하지 못해도 개폐·온도 전달과 B 서비스 통합은 진행한다. 규칙을 사용할 때는 `rule`로 표시하고 보드 AI 완료로 기록하지 않는다.

A의 상태 추정은 B의 일주일 개인 패턴 학습과 다르다. 준비된 코드로 실측 회차를 수집하는 즉시 학습을 시작할 수 있다. 실제 병목은 학습 계산 자체보다 독립된 운전 회차·조건의 확보와 실측 검증일 가능성이 크며, 소요 기간은 아직 확정할 수 없다.
