# B 서비스 배포·보존·복원 안내

기준 소스: `main` `bb419ea` (2026-10-07). 이 문서는 현재 **소스의** HA 내부 분석 모드에 대한 배포 안내다. 실제 HA 설치본과 소스의 일치는 별도 해시 대조 전까지 확정하지 않는다. 독립 작업자 모드는 HA 내부 분석과 동시에 켜지 않는다.

## 발표용 B 배포 후보 범위

현재 생성한 HA 설치 ZIP은 `dist/bapsim_ha_bundle.zip`이고 SHA-256은 `3B80D31401F7862DB8C2C47D33E3CBBF6827FA6EEC3751B0690B383E0EB5F920`이다. 통합 manifest 버전 `0.1.0`만으로는 후속 수정본을 식별할 수 없으므로 커밋과 ZIP 해시를 함께 사용한다. 이 ZIP의 B 런타임은 `bb419ea` 소스를 기준으로 만들었고, 이번 턴의 오프라인 평가 도구 수정은 ZIP 내용에 포함되지 않는다.

발표 지원 범위는 **HA 내부 분석 모드**의 검증된 입력 수집·개인 패턴·기록·실물/시험 화면 분리·보호자 알림/조작 소프트웨어로 고정한다. 독립 작업자 모드는 선택적 개발 모드이며 같은 설치에서 동시에 운영하지 않는다. 보드 맥락 설명은 HA 내부 모드만 지원한다. 실제 센서 보고의 `input_kind=test`는 운영 live 학습/알림에서 제외한다. 실사용 개인화 정확도, 외부망 폰 응답, 장시간 복원은 발표 완료 기능으로 주장하지 않는다. 현재 HA에 설치된 파일의 동일성은 별도 미확인이다.

## 보존 경계와 저장 위치

HA 설정 디렉터리를 기준으로 한다. JSONL 날짜는 UTC다.

| 경로 | 내용 | 소스의 보존 설정 |
|---|---|---|
| `.storage/bapsim.pipeline` | 개인 모델, 판단·발송·보호자 조작, 연결·설정 상태 | HA Store 상태 파일. 별도 일수 삭제가 아님 |
| `bapsim_events/` | 원시 8필드 이벤트 | 자동 기간 삭제 없음. 용량·백업 정책 필요 |
| `bapsim_observations/` | 정규화 관측 | 기본 90일 |
| `bapsim_contract_observations/` | A–B 신호별 계약 기록 | 기본 90일 |
| `bapsim_records/` | 사용 묶음·판단·서비스 기록 | 180일 |
| `bapsim_test_runs/` | 개발 시험 기록 | 7일 |
| `custom_components/bapsim/` | 설치된 B 코드 | 데이터 보존이 아니라 버전 대조·복구 대상 |

위 일수는 `ObservationJournal.prune()`의 파일 날짜 경계다. 90/180일 동안 현장에서 실행한 실적은 없다. 원시 저널에 90일 보존을 잘못 적용하지 않는다. HA의 다른 데이터베이스·Matter Fabric은 이 목록에 포함되지 않으므로 전체 HA 백업과 별도로 다룬다.

## 설치 전 백업

1. 현재 HA Core 버전, B 통합의 설치 파일 목록·해시, Matter/입력 매핑, 실행 모드, 알림 서비스 이름을 기록한다. 토큰 값은 기록하지 않는다.
2. HA의 정상 백업 기능으로 현재 구성을 먼저 백업하고 백업 파일의 위치·크기·SHA-256을 기록한다. 실제 복원 가능성을 시험하기 전까지 `백업 성공`과 `복원 검증`을 구분한다.
3. B 통합이 기록을 쓰지 않는 시점에 위 표의 상태 파일·디렉터리를 같은 시점의 사본으로 보관한다. 쓰기 중인 JSONL과 상태 파일을 시간 차 있게 복사한 사본을 일관된 복원본으로 취급하지 않는다.
4. 새 `dist/bapsim_ha_bundle.zip`의 해시와 배포 소스 커밋을 기록하고, 설치 전후 `custom_components/bapsim/` 파일 목록을 대조한다. ZIP 생성 성공은 HA 설치 성공이 아니다.

## 복원 시험과 판정

1. 현재 운영 인스턴스와 분리된 복원 환경을 준비한다. Matter Fabric이나 동일 기기 자격 증명을 복수 활성 HA에 동시에 복제하지 않는다.
2. 동일 버전의 B 코드와 같은 시점의 `.storage/bapsim.pipeline`·JSONL 자료를 복원한다. 재기동 후 통합 로드 오류와 등록 서비스/엔티티를 확인한다.
3. 복원 전후 같은 household/device에 대해 개인화 상태, 활성 사건 ID, 보류 기간, 전달 ledger의 `ha_accepted`/`failed`/`uncertain`, 저장된 알림 대상, 관측·계약·서비스 기록 수와 마지막 ID를 대조한다. 민감한 값은 공유 보고서에 복사하지 않는다.
4. 기존 복구 snapshot이나 과거 알림을 새 개방·새 발송으로 처리하지 않았는지 확인한다. 한 항목이라도 달라지면 해당 시험은 실패로 기록하고 원본 백업을 보존한다.
5. 운영 인스턴스에 복원을 적용할 필요가 있으면 하드웨어 담당과 장치 등록·Fabric 영향, HA 전체 백업 범위를 먼저 확인한다.

현장 기록은 [잔여 검증 실행표](B_잔여검증_실행표_2026-10-07.md)의 공통 버전·시험 ID 형식을 따른다. 실제 설치본 대조와 복원 결과는 아직 없다.
