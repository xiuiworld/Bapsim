# 보드 출력·상태 추정 설계서

> 이 문서는 설계·정책 기준입니다. 실제 구현/설치와 미검증 범위는 [현재 검증 요약](../IMPLEMENTATION_STATUS.md)을 확인하세요.

작성일: 2026-10-02 · 상태: 구현 착수용 설계 제안, 실기 검증 전

## 1. 이 문서에서 정하는 것

A의 보드는 **밥솥에서 직접 관측한 정보와 밥솥 운전 상태 추정**을 제공한다. B의 서비스는 이를 기록하고 사용 행동을 묶어 개인별 패턴과 알림을 판단한다. 보드에서 식사 횟수·미사용 위험·외식 여부까지 판단하지 않는다.

사용자 합의는 [기능·입출력 정의서](기능_입출력_정의서.md), 담당은 [역할 분담](역할_분담.md)을 따른다. 아래 상태명·형식은 이번에 작성한 제안이며 실물에서 이미 구분된다는 뜻은 아니다. 핀·회로·센서 임계값·최종 학습 모델은 이 문서에서 확정하지 않는다.

## 2. 센서별 관측 출력

밥솥은 CRP-G1020MP, 보드는 nRF54LM20-DK 기준이다. 광센서 GL5528은 구매 5개 중 4개 사용·1개 예비 계획이다.

| 입력 | 제안 출력 이름 | 값과 의미 | 구분해야 할 한계 |
|---|---|---|---|
| 자석 개폐센서 5C-39 NO | `lid_open` | true=실제 뚜껑 열림, false=닫힘 | NO 접점의 전기 신호와 열림 의미는 설치 방향에 맞춰 A가 변환. 잠금 해제와 다름 |
| 잠김 표시등 광센서 | `lock_led` | on / off / blinking | 잠김 표시 관측. 뚜껑 상태를 대체하지 않음 |
| 보온 표시등 광센서 | `warm_led` | on / off / blinking | 표시등 상태. 실제 보온 동작과의 관계는 검증 필요 |
| 백미 표시등 광센서 | `white_rice_led` | on / off / blinking | 메뉴 선택과 실제 취사 진행을 구분해야 함 |
| 상단 맨 왼쪽 시간 표시등 광센서 | `timer_first_led` | on / off / blinking | 예약 2시간 / 찜 10분 공유 표시. 전체 시간 표시를 읽는 센서가 아님 |
| NTC 10k B3950 VLT-THS010 | `surface_temperature_c` | 설치 지점 온도, 섭씨 실수 | 음식 내부 온도·남은 밥의 양이 아님. 설치 위치를 함께 기록 |

모든 항목은 판단할 수 없으면 값 대신 null과 사유를 제공한다. 점멸 구분은 시간 구간 관측이 필요하며, 아직 구현하지 않았다면 순간 점등을 점멸 판정으로 꾸미지 않는다. LED 점등 임계값과 개폐 흔들림 제거는 보드에서 처리한다.

예약 시간 표시는 사용자 첨부 설명서상 **예약 취사 완료까지 남은 시간**이다. 단일 LED의 점등만으로 ‘2시간 뒤 완료’, 소등만으로 ‘예약 없음’을 출력하지 않는다. 보관 설명서와 실제 모델의 적용 관계 및 점등 동작은 [하드웨어 안내](../hardware/README.md)의 확인 대상이다.

## 3. 보드 Edge AI의 첫 분류 목표

입력은 최근 일정 구간의 LED 변화·개폐·온도와 온도 변화량이다. 시간 구간 길이와 샘플링 주기는 모델 설계에서 정한다. 단일 시점의 LED만 보고 운전 상태를 확정하지 않는다.

| `cooker_phase` 제안 값 | 의미 | 사용 조건 |
|---|---|---|
| `cooking` | 취사가 진행 중일 가능성이 높음 | 온도 추이와 표시등 등 복수 관측으로 구분 가능한 경우 |
| `warming` | 보온 중일 가능성이 높음 | 보온 표시와 온도·이력의 관계가 학습·검증된 경우 |
| `inactive` | 관측 범위에서 취사·보온이 아닌 상태로 분류 | 전원 꺼짐이나 예약 없음까지 뜻하지 않음 |
| null | 판단 불가 또는 아직 제공하지 않는 기능 | 불확실, 필요한 센서 오류, 모델 미배포 등 사유를 구분 |

이 세 상태는 **첫 학습·평가를 위한 후보**다. 구분이 어려운 상태는 null로 남기거나 다음 계약 버전에서 상태 범위를 줄인다. 어려운 사례를 강제로 inactive에 넣지 않는다. 예약 관련 추정은 가능한 범위에서 추가 검토한다. 단일 시간 LED로 전체 예약 유무를 구분할 수 없으므로 예약 확정 상태를 무조건 출력하지 않는다. 취소·찜·재가열을 각각 독립 분류하는 것은 필수 범위가 아니다. 예약은 운전 상태와 별도 보조 추정으로 설계하고, 검증 전에는 현재 cooker_phase enum에 억지로 넣지 않는다.

- 관측값과 추정값은 함께 남긴다. 추정만 전달해 원인을 확인할 수 없게 만들지 않는다.
- 추정에는 방법(`edge_model` 또는 `rule`), 모델/규칙 버전을 붙인다. 규칙 대체를 AI 결과라고 표시하지 않는다.
- 모델 점수가 있으면 보조 값으로 보존할 수 있지만, 검증 전 점수를 실제 정답 확률로 표현하지 않는다.
- 입력 일부가 고장났을 때 계속 추론할 수 있는지는 모델별로 검증한다. 근거 없이 정상 점수를 유지하지 않는다.
- A가 보드 모델 학습·배포·평가를 맡고, B는 제공된 결과를 사용한다. B의 개인 패턴 학습은 별도다.

학습 기록의 정답은 실제 조작 메모와 확인 가능한 동작에 근거한다. 학습 입력인 LED 규칙을 그대로 정답으로 삼아 AI 정확도를 입증하지 않는다. 학습과 평가는 가능한 한 서로 다른 취사 회차로 나누고, 세 상태의 혼동과 판단 불가 비율을 함께 확인한다. 목표 수치는 아직 정하지 않는다.

## 4. 보드에서 보내지 않을 결론

| 결론 | 처리 위치와 이유 |
|---|---|
| 한 끼 먹음 / 정확한 끼니 수 | 출력하지 않음. 개방은 식사 가능 행동의 단서 |
| 여러 개방을 한 번의 사용으로 묶기 | B의 규칙 처리. 첫 개방부터 60분 고정 창. 뒤의 개방으로 연장하지 않음 |
| 평소보다 사용이 늦음 / 점진적 사용 감소 | B의 개인 기록·요일별 기준·장기 기준 비교 |
| 외출·외식 가능성 | B가 가용한 다른 기기 정보를 참고. 확정하지 않음 |
| 보호자 알림 발송·보류·재안내 | B의 별도 알림 정책 |
| 정확한 예약 완료 예정 시각 | 현재 센서 구성으로 보장하지 않음 |

취사 추정에서 보온 추정으로 바뀌면 B는 ‘취사 종료 추정’ 이력으로 표현할 수 있다. 실제 완료 신호를 직접 받은 것과 구분하며, 이 변화가 즉시 식사를 기대하거나 알림을 보내는 조건은 아니다.

## 5. Matter와 HA로 전달하는 범위

물리 경로는 **보드 → Thread → Nest Hub 2세대 → 가정 IP 네트워크 → HA/Matter Server**다. Nest가 Google Home의 데이터를 HA로 복사하는 구조가 아니다. Multi-Admin으로 같은 장치를 Google Home과 HA에 각각 등록한다. [HA Matter 설명](https://www.home-assistant.io/integrations/matter/)

| 정보 | 매핑 제안 | 현재 상태 |
|---|---|---|
| 실제 뚜껑 개폐 | Contact Sensor 기기 유형 + Boolean State | 표준 후보. 실제 endpoint 구성·HA 의미 변환 확인 필요 |
| 설치 지점 온도 | Temperature Sensor + Temperature Measurement | 표준 후보. 측정 위치·보정·표시 단위 확인 필요 |
| LED 관측·보드 운전 상태 추정 | 의미가 맞는 표준 모델부터 검토 | 구체 클러스터 미확정. 범용 앱 표시와 HA 수신 경로 검증 필요 |
| 센서 오류·추정 버전 등 부가 정보 | 표준 진단 정보 활용 가능성 검토 후 부족분 정의 | 미확정. 임의 표준 ID를 만들지 않음 |

Google의 지원 목록에는 Contact Sensor와 Temperature Sensor가 있으나, 이 사실이 임의 복합 장치의 모든 정보를 Google Home 화면에 표시한다는 보장은 아니다. [Google 지원 기기 유형](https://developers.home.google.com/matter/supported-devices)

LED 관측을 제공하려고 가짜 조명 스위치나 접촉 센서로 이름만 바꾸지 않는다. 표준으로 의미를 표현할 수 없는 정보에 확장이 필요하면 의미와 형식을 공개하고 A가 HA 노출 경로까지 구현·검증한다. ‘밥심 전용’이라는 이유로 추정 결과를 일부러 닫아두지 않는다. 동시에 자체 확장을 공식 밥솥 표준이라고 부르지 않는다.

**정규화 JSON은 B의 수집기 내부 형식이며, 보드가 Thread로 이 JSON을 직접 보내라는 규격이 아니다.** 확장이 미구현인 정보는 unsupported로 표시하고, 지원된 것처럼 가상 HA 엔티티를 약속하지 않는다. 세부 계약은 [A–B 데이터 계약 설계서](../contracts/AB_데이터_계약.md)을 따른다.

## 6. 기록과 제공 주기

- 실제 개폐는 흔들림 제거 후 변화가 누락되지 않도록 보고하는 것을 목표로 한다. 최종 보고 방식과 빠른 개폐 보존 여부를 확인해야 한다.
- LED·추정 상태는 변화 시 제공하는 방향으로 설계한다. 온도는 주기와 변화 폭 기준을 설정 가능하게 한다.
- 원시 ADC와 세밀한 온도 흐름은 A의 보드 학습·검증용 기록에 남긴다. 전부 상시 Matter로 전송하는 것은 기본 요구가 아니다.
- 보드 로컬 학습 기록은 센서별 원시값, 보드 단조 증가 시간, 부팅 구분, 보정/펌웨어 버전, 실제 조작 메모를 연결할 수 있어야 한다. 구체 파일 형식은 별도 정의한다.
- 샘플링·보고·연결 확인 주기는 Matter·HA 명세의 시험 시작값을 참고하고 실기로 확정한다. ‘일정 시간 이벤트 없음’을 곧바로 미사용 또는 고장으로 처리하지 않는다.

## 7. 지금 진행 가능한 작업과 남은 확인

지금 B는 계약의 가상 입력으로 수집 이후 로직을 작성할 수 있고, A는 관측·추정 상태를 이 목록에 맞춰 설계할 수 있다. 하드웨어 시험을 기다려야만 문서나 분석 코드를 시작할 수 있는 구조가 아니다.

후속 확인은 센서별 극성·보정과 설치 위치, 모델로 구분 가능한 상태, SDK/HA 버전별 표준 지원, 추가 정보의 HA 노출, 빠른 개폐 보고 보존이다. 확인 결과에 따라 매핑을 갱신하되, 값의 의미를 바꿀 때는 계약 버전도 변경한다.
