# 팀 상세 설계 합의안

2026-10-02 · **팀 대화 및 최종 사용자 동의 반영본. 설계 합의와 구현 검증은 별개다.**

## 1. 이 문서부터 읽기

기존 아키텍처는 사용자가 정한 방향으로 유지한다. 이번에는 그 안에서 구현할 인터페이스·정책·운영 방식을 한 번에 검토할 수 있도록 작성했다. 모든 세부 구현을 두 사람이 공동 결정할 필요는 없다. 사용자 경험·서로의 인터페이스·작업량·비용에 영향을 주는 것만 합의표에 올렸다.

이미 합의한 것: A의 장비·HA/Matter 환경·보드 Edge AI, B의 기록·개인 분석·보조 정보·폰 화면/알림, Nest를 통한 Thread 연결, Google Home+HA Multi-Admin, Companion 앱 활용, 소분·냉동 주 사용자 제외, 실제 식사 확정 금지, 로컬 개인화, 방해금지와 사용 재개 처리 원칙. 이 내용을 다시 찬반 결정할 필요는 없다.

## 2. 구간별 문서 지도

```text
센서·보드
  └─ Matter 기기 모델·보고 ─────────── [1]
       └─ HA 노출·단위/품질 변환 ───── [1]
            └─ B 정규화 입력 JSON ─── [2]
                 └─ 행동·개인 분석·정책 [3]
                      └─ 결과 → HA → 폰 [4]
설치·등록·복구·끝까지 시험 ──────────── [5]
```

| 번호 | 문서 | 읽을 사람·내용 |
|---|---|---|
| 1 | [Matter·HA 연동 명세](../contracts/Matter_HA_연동_명세.md) | A 중심, B 인터페이스 확인. Endpoint·표준/확장·HA 노출·보고 |
| 2 | [HA 수집 이후 분석 입력 계약](../contracts/AB_데이터_계약.md) | B 중심, A 의미 확인. 기존 JSON은 이 구간 |
| 3 | [분석·알림 정책](분석_알림_정책.md) | 공동. 개인화·첫 안내·재안내·야간·감소 추세 |
| 4 | [분석 결과·HA·휴대폰 출력 계약](../contracts/분석결과_HA_휴대폰_출력계약.md) | B 중심, A 환경 확인. 상태·알림·화면·중복 방지 |
| 5 | [설치·운영·통합시험 계획](설치_운영_통합시험_계획.md) | 공동. 등록·외부 접속·복구·20개 시험·심사 증거 |

센서별 의미와 보드 분류 후보는 기존 [보드 출력 설계서](보드_출력과_상태_추정.md)을 유지한다. 최종 대화와 “얘기 안 나눈 것은 설명에 동의”한다는 사용자 확인을 반영했다. 범위·행동 원칙은 아래 결정을 따르며, 감소 임계값 등 검증용 후보 수치는 확정된 성능 기준이 아니다.

## 3. 팀이 결정할 항목

아래 14개 항목의 팀 결정은 완료했다. 구현으로 확인할 사항과 조정 가능한 수치는 별도로 남긴다. “미검증”은 팀이 아직 방향에 합의하지 않았다는 뜻이 아니다.

| ID | 결정할 것 | 추천안과 이유 | 주요 대안·영향 | 최종 결정 |
|---|---|---|---|---|
| D01 | Matter 기본 모델 | 상태 확인용 장치, 실제 개폐·온도 표준 Endpoint. 원격 취사 제어 없음 | 표시 이름은 밥심/밥솥으로 가능. 표준 기기 유형과 제품 이름은 별개 | 합의 반영 |
| D02 | 보드 추정 범위 | 취사·보온·비활성·판단 불가 + 가능한 범위의 예약 관련 추정 후보 | 단일 시간 LED로 예약 유무 전체를 판별하지 않음. 예약 구현 가능성·표현은 검증 대상 | 합의 반영 |
| D03 | 표준·확장 | 표준 의미를 우선하고 부족분만 공개 확장. A가 HA 수신까지 담당 | 정확한 확장 항목·SDK/HA 경로는 기술 확인. 임의 확장을 공식 표준으로 부르지 않음 | 합의 반영 |
| D04 | 분석 결과 반환 | 로컬 MQTT 상태 + HA 알림 서비스 | 보드 Matter 경로는 유지. 실제 환경 설치·검증 전 | 합의 반영 |
| D05 | 행동 묶음·개인화 | 첫 개방부터 60분 고정 창, 뒤의 개방으로 연장 안 함. 개인화는 추천 방향 채택 | 경계는 [시작, 시작+60분). 실제 끼니가 아닌 사용 묶음. 정상 관측·자료 충분성 확인 | 합의 반영 |
| D06 | 첫 생활 변화 안내 | 연속 사용 공백 / 며칠간 사용 감소의 두 종류. 규칙적 사용은 두 예상 창 연속 미관측 시 후보 | 시간 조금 변한 것만으로 푸시하지 않음. 불규칙형은 개인 사용 간격 기준 | 합의 반영 |
| D07 | 감소·보조 정보 | 하루 변화는 추세로 단정하지 않음. 보조 활동은 제한적으로 보류 근거 | 30%·3일 등 수치는 평가용 후보. 가상 보조 입력만 사용 | 합의 반영 |
| D08 | 야간·보호자 조작 | 야간 보류 유지, 요약→상세 화면. 확인했어요 및 기간 지정 알림 쉬기 포함 | 확인은 안전 판정 아님. 쉬기 종료 시 재평가, 여행 구간은 정상 학습에서 구분 | 합의 반영 |
| D09 | HA 환경 | A의 Galaxy Book3 Pro / Windows 10 Pro에서 HA OS VM+Matter Server 방향 채택 | 노트북 정보는 사용자 진술. 실제 자원·네트워크·설치 상태 미검증. B 서비스 전달 방식 유지 | 합의 반영 |
| D10 | 외부 접속 | HA Cloud 무료 체험 사용 | 계정/체험 시작은 아직 실행하지 않음. 시작·종료일 확인, 자동 유료 전환 가정 금지 | 합의 반영 |
| D11 | 보조 기기 | 실제 추가 기기 없이 가상 입력으로만 보조 맥락 검증 | 실제 밥심의 Google Home+HA Multi-Admin은 그대로 수행. 실제 타사 센서 연동과 구분 | 합의 반영 |
| D12 | 기록 보존 | 정규화 관측90일, 행동·기준·판단·발송180일. 익명 기록 공유 | A 환경·접근 설정, B 수집·저장 코드의 기존 역할 유지 | 합의 반영 |
| D13 | 오픈소스 | 문서·예제뿐 아니라 코드 공개 방향 채택 | 아직 게시하지 않음. 공개 전에 비밀·개인기록 제외, 의존성 권리와 라이선스 확인 | 합의 반영 |
| D14 | 통합 완료 | 실제 폰·외부 상세 접속 포함 시험 계획 채택 | 확인/기간 쉬기 시험 추가. 가상 보조 정보는 가상이라고 명시. 실제 시험은 미실행 | 합의 반영 |

D05~D08의 수치들은 정책 파일에서 변경 가능하게 만드는 것이 추천이다. 모든 작은 파라미터 조정을 회의 안건으로 만들 필요는 없지만 사용자에게 알리는 시점이 크게 달라지면 함께 확인한다.

## 4. 합의와 별개로 확인할 기술 항목

| 확인할 사실 | 담당 | 왜 찬반으로 해결할 수 없는가 |
|---|---|---|
| nRF54LM20-DK와 선택 SDK의 실제 지원·메모리·모델 실행 | A | 실제 빌드/실행·자원 확인 필요 |
| 제조사 확장 데이터의 Matter Server→HA 노출 가능성 | A | 문서·버전·샘플 구현 확인 필요. 현재 가장 큰 연결 불확실성 |
| LED 의미·NTC 보정·설치·접점 극성 | A | 실제 신호와 비교 필요 |
| 빠른 개폐 이벤트 보존·구독/재연결 동작 | A+B | 기본 상태 조회만으로 누락 여부를 보장할 수 없음 |
| HA 엔티티·폰 알림·외부 상세 접근 | A+B | 각 OS/설치 환경에서 확인 필요 |
| 개인화가 고정 규칙보다 유용한지 | B | 동일 자료 비교 필요. 설계만으로 성능 입증 불가 |

정확한 핀·저항 연결·학습 라이브러리·모델 구조·DB 구현·실제 entity_id는 담당자가 선택하고 인계 문서에 남긴다. 입력 의미나 역할 범위를 바꾸지 않는 한 둘이 매번 합의할 항목은 아니다.

## 5. 검토 결과 기록 양식

아래를 복사해 결정만 적으면 된다. 회의가 반드시 필요한 것은 아니다.

```text
검토일:
검토자: A / B
추천안 채택: D...
수정할 항목: D... → 변경 내용 / 이유
기술 확인 후 결정: D... → 확인 담당 / 필요한 증거
다음 구현 버전:
```

본 문서는 최종 사용자 동의로 합의를 반영했다. 다음 단계는 각 담당자의 구현과 기술 확인이다. 새 형식·정책 변경 시 버전과 이유를 남긴다. 실제 구현 성공·성능 검증·공개 게시 완료를 뜻하지 않는다.
