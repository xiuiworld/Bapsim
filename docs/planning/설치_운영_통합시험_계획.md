# 설치·운영·통합시험 계획

> 이 문서는 설계·정책 기준입니다. 실제 구현/설치와 미검증 범위는 [현재 검증 요약](../IMPLEMENTATION_STATUS.md)을 확인하세요.

## 1. 실행 환경 추천

A 노트북에 **HA OS 가상 머신 + 공식 Matter Server**, 별도 밥심 분석 서비스를 두는 안을 우선 검토한다. HA 공식 문서는 HA OS의 Matter 설치를 권장한다. VM은 가정 LAN과 IPv6·mDNS 통신이 가능한 연결을 구성해야 하며, 단순 NAT 격리로 해결됐다고 가정하지 않는다. [HA Matter 안내](https://www.home-assistant.io/integrations/matter/)

분석 서비스와 MQTT 브로커의 실행 위치는 해당 네트워크에서 HA와 상호 접근되게 정한다. B는 학습 모델과 실행 코드를 기존 합의대로 Docker 이미지와 설정·실행 안내로 전달한다. 이것이 HA까지 같은 방식으로 설치해야 한다는 뜻은 아니다.

실제 노트북 자원·현재 HA 설치 여부는 아직 확인하지 않았다. D09의 설치 방향은 채택했으며 A가 실행 전 확인하고 이미 작동하는 환경이 있다면 불필요하게 갈아엎지 않는다. 버전 묶음에는 펌웨어·보드 모델·SDK·HA·Matter Server·B 서비스·정책·데이터 계약을 함께 기록한다.

## 2. 최초 설치·Multi-Admin

설치 전에 자녀와 함께 대상 생활 방식을 확인한다. 밥솥에서 밥을 꺼내 먹는 독거노인을 대상으로 하며, 취사한 밥을 주로 소분·냉동해 이후 식사를 밥솥 개방으로 관측할 수 없는 경우는 이번 시연·평가 대상에서 제외한다. 개방 간격만으로 소분 여부를 자동 판별하지 않는다.

1. A가 Nest Hub와 가정 네트워크를 준비한다. 노트북은 Wi-Fi 또는 LAN, Nest Hub 2세대는 Wi-Fi 경로로 계획한다.
2. 개발용 VID/PID·시험 계정·Google 개발자 프로젝트 조건을 맞춘다. 등록 QR·설정 코드는 비공개 보관한다.
3. 보드를 Google Home에 먼저 등록한 뒤 공유 절차로 HA에 추가하는 순서를 추천한다. 같은 노드가 두 Fabric에 등록되는지 확인한다. 등록 순서를 반대로 할 필요가 생기면 원인과 절차를 남긴다.
4. HA 표준 엔티티·확장 정보 노출을 확인하고 A가 매핑을 인계한다.
5. B 수집기와 분석을 연결하고 실제 데이터 mode=live, 가상 데이터 mode=simulation을 분리한다.
6. 자녀 역할 휴대폰에 Companion 앱을 등록하고 알림 권한·대상 서비스를 설정한다.
7. 외부망 알림 수신과 상세 화면 접속을 각각 확인한다.

Google 개발 장치 조건은 [공식 시작 안내](https://developers.home.google.com/matter/get-started), Multi-Admin 절차는 [HA Matter 안내](https://www.home-assistant.io/integrations/matter/)를 참고한다. 표준 개폐 상태를 양쪽에서 확인하는 것을 상호운용 최소 목표로 삼고, 구글이 확장 상태까지 표시한다고 약속하지 않는다.

## 3. 외부 접속 추천

외부 접속은 **Home Assistant Cloud 무료 체험을 사용**하기로 합의했다. 계정 등록·체험 시작은 아직 실행하지 않았다. A가 실제 시작일·만료일과 발표 일정의 관계를 확인하고, 만료 후 유료 유지나 VPN 전환은 자동으로 진행하지 않는다. [HA 원격 접속 안내](https://www.home-assistant.io/docs/configuration/remote/)

VPN은 현재 채택한 방식이 아니며 이후 대안이 필요할 때 검토한다. 보안 설정 없이 외부로 HA 포트만 공개하는 방식을 기본안으로 삼지 않는다. Matter·개인 분석은 로컬로 유지하되 외부 푸시/원격 접속에는 인터넷·선택 서비스 의존성이 있다. ‘완전 무클라우드 알림’으로 발표하지 않는다.

## 4. 장애·복구 동작

| 장애 | 기대 동작 | 담당 |
|---|---|---|
| 센서 하나 오류 | 해당 값만 사용 제한, 다른 관측은 유지. 추정 입력 충분성 재판정 | A 상태 제공, B 품질 처리 |
| 보드 재부팅 | BootId/기준 재설정, 복구 snapshot을 새 개방으로 세지 않음 | A+B |

| HA/Matter Server 재시작 | 재구독·엔티티 재확인, 과거 이벤트 중복 집계 방지 | A+B |
| B 프로세스 중단 | HA에 결과 만료/분석 불가 표시. 재시작 후 저장된 판단·발송 이력 복원 | B |
| 인터넷 단절 | 가능한 로컬 수집·분석 유지. 폰 발송 실패 기록, 복구 후 낡은 알림 일괄 발송 금지 | A 네트워크, B 발송 |
| MQTT 중단 | 화면 갱신 불가 표시, 복구 후 현재 상태·discovery 복구 | A+B |
| Fabric 하나 제거 | 다른 플랫폼 등록을 의도치 않게 제거하지 않음. 제거 범위 확인 | A |

백업은 A가 HA 설정·Fabric 관련 복원 가능 범위를, B가 기록·개인 기준·정책·발송 이력을 책임진다. 복원한 Fabric 정보를 여러 활성 인스턴스에 동시에 복제하지 않는다. 새 기기를 기존 device_id에 잘못 붙여 타 가정 기록과 섞지 않는다.

## 5. 인계 묶음

A → B: 신호 매핑, 지원/미지원, 버전표, 익명 관측 파일, 실제 조작 시각·행동 메모, 연결/센서 상태. B → A: 실행 버전, 모델/정책, 설정 예시, HA 화면·알림 설정, 실행/중지/로그/복원 안내, 재현 시나리오.

B가 요청할 실기 시험은 시나리오 ID·조작 순서·기대 로그·필요 시간을 적어 묶어서 전달한다. A는 같은 ID로 결과를 남긴다. 이미 공유된 기록으로 재현 가능한 문제는 B가 먼저 분석한다. 보드 Edge AI 학습·배포는 A, 개인 패턴 학습·서비스는 B라는 기존 역할은 유지한다.

## 8. 구현 순서

1. 채택한 D01~D14에 맞춰 담당별 구현. 확장 수신 경로 등 기술 확인부터 기록.
2. A는 SDK/HA 수신 경로 검토, B는 가상 입력·정책·출력 계약으로 병행 개발.
3. 첫 수직 연결은 표준 개폐 → 정규화 → 개발용 판단 → 실제 폰 알림·상세 화면으로 확인.
4. LED/Edge AI·개인화·보조 입력을 연결하고 위 시험을 누적.
5. 발표 버전 조합과 로그를 고정하고 재시작·시연 장소 네트워크를 점검.

센서 도착을 기다리면서도 1~3의 소프트웨어 설계·가상 입력 경로를 진행할 수 있다. 실기 확인이 필요한 부분을 문서상으로 완료 처리하지 않는다.

현재 노트북은 사용자 진술상 Galaxy Book3 Pro / Windows 10 Pro다. 실제 OS·자원·HA 설치 상태는 이 문서 작성 중 확인하지 않았다. 코드까지 공개하는 방향을 채택했으며 공개 전 라이선스·의존성 권리·비밀/개인기록 제외를 확인한다.
