# 실물 밥솥 연결 가이드

이 문서는 밥솥 장비가 준비됐을 때 밥심의 Home Assistant(HA) 수신 경로에 연결하는 순서다. 현재 밥심의 입력 변환·분석·상태 화면은 준비됐지만, **이 Windows Docker 개발 환경에는 Matter Server와 실물 기기가 연결돼 있지 않다.** 따라서 지금 상태를 ‘밥솥만 오면 바로 사용 가능’으로 보지 않는다.

실험할 때 [실물 Matter 수신 검증 기록](실물_Matter_수신_검증_기록.md)에 실제 HA 값과 이벤트 시각을 남긴다.

하드웨어 인계에서 확인된 계획은 자석 뚜껑 접점, 열림/잠김·보온·백미 LED 광센서, NTC 온도센서다. 취사 시작·완료는 이 신호들로 아직 검증되지 않았다. [인계 반영 기록](하드웨어_인계_반영_2026-10-02.md)에 센서별 확인 항목을 정리했다.

사용자 제공 [시스템 아키텍처 v0.2](reference/밥심_시스템_아키텍처_v0.2.md)는 구글 네스트 허브 2세대를 Thread Border Router로 사용하고, 보드의 관측값과 Edge AI 추정값을 함께 Matter로 제공하는 목표를 추가했다. HA에서 실제 엔티티가 확인되면 [구현 대조](아키텍처_v0.2_구현_대조.md)의 `register_matter_board_signal`로 각각 원시 이력을 남긴다. 이것만으로 취사 상태의 물리적 의미가 검증되지는 않는다.

## 장비 도착 전에 준비할 것

1. Matter가 동작하는 HA 환경을 정한다. [HA 공식 Matter 안내](https://www.home-assistant.io/integrations/matter/)는 HA OS와 공식 Matter Server 앱 구성을 권장한다. HA Container와 별도 Matter Server는 가능하지만 공식 지원 범위가 제한된다. 현재의 Windows Docker localhost 구성은 시뮬레이션용으로 유지하고, 실물용 HA 호스트를 별도로 마련하는 편이 안전하다.
2. 실물용 HA 호스트와 휴대폰이 같은 로컬망에서 기기를 발견할 수 있어야 한다. Matter에는 로컬 IPv6와 mDNS가 필요하다. Thread 기반 밥솥이면 Thread Border Router도 필요하다. [Docker Desktop 호스트 네트워크 설명](https://docs.docker.com/engine/network/drivers/host/)도 Desktop의 호스트 네트워크가 TCP/UDP 계층만 지원한다고 명시한다. 현재 Windows Docker에서 Matter 발견을 검증한 것으로 간주하지 않는다.
3. Nordic 담당에게 Matter 페어링 코드/QR, 전원·리셋 방법, 보드/SDK 버전, 센서별 Matter 속성과 HA 엔티티, 실제 동작 로그를 요청한다. 뚜껑만 노출되면 핵심 취사·개방 분석을 실물로 검증할 수 없다.
4. 실물용 HA에 밥심 통합을 배포하고 `check_config`를 실행해야 한다. `python -m tools.build_ha_bundle`로 만드는 [배포 ZIP](../dist/bapsim_ha_bundle.zip)은 `custom_components/bapsim`과 분석 코어를 함께 담는다. 실물 HA 설정 디렉터리에 압축을 풀고 `configuration.yaml`에 `bapsim:`을 추가한다. 현재 개발 컨테이너에서 별도 HA 호스트로의 이전은 아직 수행하지 않았다. 보호자 휴대폰 푸시는 별도로 Companion 앱과 알림 대상 등록이 필요하다.

## 연결 당일: 기록할 값

| 항목 | 실제 장비에서 확인할 내용 |
| --- | --- |
| 밥솥 ID | 두 입력에 공통으로 쓸 `device_id` (예: `cooker_01`) |
| 뚜껑 엔티티 | HA의 `binary_sensor.*` 엔티티 ID |
| 뚜껑 방향 | 실제 열림에서 HA가 `on`인지 `off`인지 |
| 취사 엔티티 | HA의 `sensor.*`, `binary_sensor.*` 또는 `select.*` 엔티티 ID |
| 취사 상태값 | 실제 시작·완료 때 표시되는 **정확한** 두 값 |
| 가용성 | 전원/연결 단절 때 두 엔티티가 `unavailable` 또는 `unknown`으로 바뀌는지 |
| LED·온도 | 각 센서의 Matter endpoint/attribute, HA entity, 단위, 오류·미확정 표시, 실제 동작과의 대응 |

값을 추측해 등록하지 않는다. 특히 백미 LED 점등만으로 취사 시작, 보온 LED 점등만으로 완료를 뜻한다고 가정하지 않는다. 취사 완료가 HA 엔티티에서 구별되지 않으면 밥심에 가짜 완료 이벤트를 공급하지 않는다.

## HA에서 등록

Matter 통합으로 기기를 페어링하고 위 표의 값을 실물 동작으로 확인한 뒤, HA **개발자 도구 → 동작**에서 뚜껑 서비스를 실행한다. 아래 ID는 **형식 예시**이며 실제 값으로 바꿔야 한다.

```yaml
action: bapsim.register_matter_contact
data:
  device_id: cooker_01
  entity_id: binary_sensor.example_lid
  on_is_open: true
```

취사 시작과 완료를 각각 뜻하는 **서로 다른 HA 상태값**이 실측으로 확인된 경우에만 `bapsim.register_matter_cooking_state`를 실행한다. `running`/`idle` 같은 일반 상태명을 확인 없이 쓰면 취소·대기와 완료를 혼동할 수 있다. 호출 필드는 `device_id`, `entity_id`, `started_state`, `finished_state`이며 정확한 실측 문자열을 입력한다.

두 등록은 저장되어 HA 재시작 후 현재 상태를 다시 읽는다. 등록하려는 엔티티는 HA의 Matter 통합에서 온 것이어야 하며, 다른 integration의 엔티티는 거부한다. 복원된 매핑의 출처가 바뀌면 `source_unverified`로 표시하고 입력을 중단한다. 한쪽이 미등록이거나 사용할 수 없으면 해당 밥솥 분석 입력 전체를 `offline`으로 처리한다. 접점만 연결된 첫 단계에서도 `bapsim_raw_event`에는 `lid_state=open/closed`가 나타난다. 이때 `availability=offline`은 **밥솥 분석 입력이 아직 완전하지 않다**는 뜻이고, 접점 관측값은 `quality=observed`로 보존된다. `bapsim_cooker_event`에는 개방 행동을 발행하지 않는다. **밥심 실험실 → 밥심 상태 → 실물 밥솥 입력 준비**에서 `not_configured`, `missing_input`, `source_unverified`, `state_unmapped`, `entity_unavailable`, `ready` 중 현재 상태를 확인한다. `state_unmapped`는 실제 HA 값이 등록된 열림/닫힘 또는 취사 시작/완료 값과 맞지 않는 경우다. `devices` 속성의 현재 `lid_state`/`cooking_state`를 실측 기록에 옮겨 적고, 의미를 확인하기 전에는 매핑을 추측해 수정하지 않는다. `ready`는 출처와 두 HA 엔티티 상태가 확인됐다는 뜻이며 센서 동작을 검증했다는 뜻은 아니다.

노드 또는 구성요소가 바뀌면 **같은 `device_id`로 바뀐 입력의 등록 서비스만 다시 실행**한다. 예전 엔티티 연결은 자동으로 교체된다. 구성요소를 없앤 경우에는 아래처럼 제거하고, 새 입력을 찾기 전까지 `missing_input`으로 둔다.

```yaml
action: bapsim.unregister_matter_input
data:
  device_id: cooker_01
  input_type: cooking
```

`input_type`은 `lid`, `cooking`, `all` 중 하나다. 뚜껑과 취사가 서로 다른 물리 노드에 있어도 같은 논리적 밥솥이면 같은 `device_id`를 사용한다. 취사 값이 엔티티의 속성이나 별도 이벤트에만 있다면 현재 서비스에 임의의 값을 넣지 않고 어댑터를 그 형태에 맞게 조정해야 한다.

## 실물 검증 순서

1. 뚜껑 접점만 등록한 첫 시험에서는 HA **개발자 도구 → 이벤트**에서 `bapsim_raw_event` 수신을 시작한다. 실제 닫힘·열림 때 `lid_state` 값, `device_id`, `source=matter`, 수신 시각을 기록한다. 이 단계의 `availability=offline`과 `missing_input`은 예상 상태다. 취사 입력까지 검증·등록한 뒤에는 `bapsim_cooker_event`에서 `lid_opened`를 확인한다. 접점 확정에는 2초가 필요하다.
2. 메뉴 선택만 함, 실제 취사 시작, 취소, 완료·보온 전환을 구분해 사람의 시간 기록과 센서/HA 로그를 대조한다. 시작·완료가 검증되어 등록됐다면 `cooking_started`와 `cooking_finished`가 각각 한 번씩 나오는지 확인한다. 상태값이 구별되지 않으면 취사 입력 설계부터 다시 확인한다.
3. 취사 완료 뒤 첫 뚜껑 개방으로 세션과 첫 개방 지연이 생성되는지 확인한다.
4. 밥솥 연결을 끊고 복구해 `device_offline`/`device_online`과 데이터 공백 처리를 확인한다. HA 재시작 후 현재 상태 복원도 확인한다.
5. 로컬 HA 알림·보호자 응답을 확인한다. 휴대폰 Companion 앱 등록 후에는 셀룰러 환경의 실제 푸시 수신과 액션 응답을 따로 확인한다.

Matter 수신, 밥심 판정, 휴대폰 수신은 각각 별도 완료 항목이다. 연결 기록에는 각 단계의 실제 시각과 HA 엔티티값을 남긴다.
